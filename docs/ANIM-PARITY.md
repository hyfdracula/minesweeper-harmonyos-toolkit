## 一、审计基准在哪

### 1.1 原版的「权威定义」是什么

微软从未公开 Win7 扫雷源码，`Minesweeper.exe` 是闭源的。
**原版的 UI XML（`UI/*.xml`）也拿不到** —— 移植素材目录的交接文档写得很明白：

> `C:\Users\19161\Desktop\minesweeper-refs\README.md:257-258`
> 「那是原版 UI XML 和原始资源目录，作者没上传（版权）。所以拿不到 `UI/*.xml`
> 原始动画定义，但有合成好的 sheet + Theme.h 里的坐标，够用。」

所以本次审计的权威基准是**两份东西的交叉验证**：

| 基准 | 路径 | 性质 |
| --- | --- | --- |
| 原版素材 | `minesweeper-refs\win7-assets\images\*.png` | **从原版游戏里提取出来的原始精灵表**，逐字节可比 |
| 行为定义 | `minesweeper-refs\linux-minesweeper-main\src\ui\Theme.h` | Qt6 复刻，注释明确写着坐标与时长都来自原版 UI XML |

`Theme.h` 的文件头把这句话说得很清楚（`Theme.h:22-24`）：

> 「All rects here are in the logical 1x coordinates of the original UI XMLs
> (UI/*.xml in more-resources); multiply by kScale to address the stored pixels.」

`linux-minesweeper` 在移植目录里的定位是「**最完整的 Win7 行为复刻**」
（`README.md:34`），移植路线里也把它列为「移植主力」。

这就是为什么原版要分 x0=0 / x0=364 两个基址，**我们也分开取**

### 3.5 扫描条的裁剪

（`BoardWidget.cpp:702-703,727-735`）。

（`Anim.ets:263-268`：按 `srcH/barH` 的比例把可见段映射回源 y）。
两者在数学上等价（同一个线性拉伸 + 同一条裁剪边界），只是实现方式不同。

## 四、总时长：我们比参考实现更贴 XML（不是不一致）

| 动画 | 原版 XML 标称 | 参考实现实际 | 我们 |
| --- | --- | --- | --- |
| 爆炸 | 1 秒 / 23 帧 | 990 ms（`1000/30 = 33` tick × 30 ms） | **1000 ms** |
| 拆雷 | 2 秒 / 38 帧 | 1980 ms（`2000/30 = 66` tick × 30 ms） | **2000 ms** |
| 扫描条 | 3 秒 | 3000 ms（`3000/30 = 100` tick） | 3000 ms |

参考实现把秒数换算成 30 ms 的 tick 网格（`BoardWidget.cpp:22,42-44`），
于是丢了 10 ms / 20 ms 的余数。我们按 XML 的精确值实现，**帧号推进公式两者等价**：

* 参考：`frame = (tick - start) * 23 / 33`，而 `elapsed = tick*30` → `frame ≈ elapsed*23/990`
* 我们：`frame = floor(elapsed / (1000/23))` = `floor(elapsed*23/1000)`

两者差 1%，逐帧号完全对得上（上一轮慢放抓帧认出的帧号 1→22 就是这个公式算出来的）。

**结论：这一项不算差异，我们更准。**

## 五、发现的 3 处行为差异（都在 `GameController.ets`，本轮只报告）

### D1. 拆雷光束的**起跳时刻**（差得最明显，建议 lead 定夺）

* 原版/参考：`start(r) = kScanTicks * (rows - r) / (rows + 1)`
  （`BoardWidget.cpp:244`）——**按行号均匀分配**，
  底部行在 1/(rows+1)、顶部行在 rows/(rows+1) 处开火。
* 我们：`start = (条的上沿扫到该行上沿的时刻) * 3000`
  （`GameController.ets:1077-1080`），用的是**条的真实高度**
  `barH = 棋盘宽 × 62/275`（`GameController.ets:677-680`）。

两种算法在 9×9 初级局上的差（条高 2.03 格）：

| 行 r（0 = 顶） | 我们 | 参考 |
| --- | --- | --- |
| 0 | 2324 ms | 2700 ms |
| 3 | 1324 ms | 1800 ms |
| 6 | 324 ms | 900 ms |
| 7 | **0 ms** | 600 ms |
| 8 | **0 ms** | 300 ms |

**我们这边最底下两行的雷会在 0 ms 同时开火**（参考是 300/600 ms 依次开火）。
盘面越大差得越多：16×16 时我们最底 4 行同时开火，30×24 时最底 6 行同时开火。

根因：参考实现画条时用真实条高（2~5 格），但**排光束时刻时按「条高 = 1 格」推**，
（把 `start = kScanTicks*(rows-r)/(rows+1)` 反推回去，得到的正是「条高 = 1 格」的几何关系）；
我们两处都用真实条高，**自洽但底部会挤在一起**。

**建议**：把 `GameController.ets:1077-1080` 换成参考实现的行号公式即可
（一行改动，不碰 Anim.ets）：

```ts
// 参考实现：BoardWidget.cpp:244  start = kScanTicks * (rows - r) / (rows + 1)
const startMs = Math.round(Anim.SWEEP_MS * (e.rowCount - r) / (e.rowCount + 1));
times.push(startMs);
```

> 说明：**原版的 XML 拿不到**（§1.1），所以「哪条更接近原版」无法证明。
> 参考实现是「最接近 Win7 行为复刻」，但它这一条和自己的条高不自洽；
> 我们这一条自洽、但底部几行会同时炸。两个都说不通时才需要拍板，
> 这次的差异属于「两个都不完全确定」那一类，请 lead 定。

### D2. 判负时的爆炸**级联**

* 参考：**踩中的那颗先炸，其余没插旗的雷按冲击波环到达的时刻依次炸**
  （`BoardWidget.cpp:167-206`；起跳 = `max(1, round(距离 × 5))` tick，
  `kRingStagger = 5`，见 `BoardWidget.cpp:30`；被插旗的雷不炸）。
* 我们：**只炸踩中的那一颗**（`GameController.ets:1036` 的 `Anim.startTrip(cell)`，
  `Anim.tripCell` 是单个格索引，`GameController.ets:563` 只在这一格上播）。

影响：判负时原版是一片雷接连炸，我们是一颗。

### D3. 爆炸的**绘制层级**

* 参考：爆炸在**整块棋盘画完之后**单独画一遍
  （`BoardWidget.cpp:751-775`，注释：「painted over the grid so each fireball can
  spill across its neighbours' tiles」）。
* 我们：在**格子循环内部**画（`GameController.ets:563-572`），
  于是**后画的邻格会盖住爆炸溢出到邻格的那部分**。

实测证据（上一轮慢放抓的帧 `docs\verify\ANIMF_exp_x5_c0_00.jpeg`，爆炸格 (3,8)）：
爆炸精灵 57×57、偏移 (-18,-18)，确实越出格子边界，
在棋盘右沿外面能看到溢出的光晕 —— 越界处没人盖，但**格子内侧的溢出部分会被邻格盖住**。

### D4. 问号 / 旗帜：**原版没有小动画**，我们也没有 —— 一致

原版里旗和问号就是棋盘表上的**静态叠加层**（`Theme.h:88-89`，18×18），
参考实现也只画一帧（`BoardWidget.cpp:630-636`）。
标记是三态循环：无 → 旗 → 问号 → 无（`game\Board.cpp:141-153`），问号格被翻开时清掉。
我们的实现：`Theme.ets:41-47` 的矩形一致，`GameController.ets:597-598` 画问号，
选项里可开关问号（`GameController.ets:1600,1674-1676`）。**一致。**

## 六、顺带查明的一条资源事实（解释上一轮没抓到的帧）

**花园开花序列的第 0 帧是全透明空图**（该 36×36 区域内不透明像素 = 0）。

* 这不是我们的 bug，是原版资源本身如此 —— 原版画的也是这张空图，**行为一致**。
* 但它有个取证上的后果：**空帧无法用模板匹配「认出」**（对任何模板都一样不像），
  所以上一轮 `docs\ANIM-FRAMES.md` 里花园序列「没抓到第 0 帧」，
  原因就在这里，而不是快门慢。
* 同理，爆炸序列的第 23 帧位是空的，所以爆炸的第 0 帧是能认的
  （上一轮也确实没抓到，第 0 帧是另一个原因：点击命令本身要 485 ms）。
