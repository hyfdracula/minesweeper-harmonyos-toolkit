## 一、已确证（带像素/帧证据）

### 1.1 胜利扫描条会出现，并且自下而上扫过棋盘

| 证据 | 内容 |
| --- | --- |
| 修复后 `docs\verify\ANIM_win_00.jpeg` | 条**压在棋盘第 1 行上**（在棋盘矩形内） |
| 修复后 `docs\verify\ANIM_win_01.jpeg` | 条已经扫过顶端，消失 |
| 模板匹配（`tools\anim_analyze.py`） | 高光带位置 **y=522**，相似度 **0.990** |
| 帧间像素差 | `ANIM_win_00` → `ANIM_win_01` 棋盘区 **636 571** 个像素变化，maxdiff=255 |

扫描条不是用肉眼认的：把 `otherSheet.png` 上扫描条精灵（逻辑坐标 `[0,912,275,62]`）
里 alpha ≥ 200 的那几行（蓝白高光带）取出来，横向拉成棋盘宽，
当一维模板在屏幕上逐行比对，取相似度最高的那一行。
棋盘上其它东西（淡色地板、菜单栏）的相似度都在 0.94 以下，条是 0.99。

### 1.2 拆雷光束在播（38 帧那套）

- 修复后 `docs\verify\ANIM_win_01.jpeg`：**4 个格子泛着青白色光**，
  就是光束精灵（`otherSheet` 逻辑坐标 `[52*(f%7), 152*(f/7), 50, 150]`，
  共 38 帧）的当前帧。同一批格子在 `ANIM_win_00.jpeg` 里是被扫描条压住的，
  说明「条扫到哪一行、哪一行的光束就起跳」这条接通了。
- 光束精灵自带一份该格的方砖副本，扫过之后那一格会留下**褪色的雷** ——
  原版就是这个效果，我们的截图里能看到。

### 1.3 胜利后全盘被雷盖住（10 颗雷全部插旗）

- `docs\verify\ANIM_win_01.jpeg`（9×9 / 10 雷的局）里数得出来：
  第 3 行 2 面 + 第 4 行 2 面 + 第 6 行 3 面 + 第 7 行 3 面 = **10 面红旗**，
  非雷格全部揭开。
- 这条是**引擎与动画接通的硬证据**：引擎 `MinesweeperEngine.checkWin()`
  在判胜时给所有雷自动插旗（`cell.mark = Mark.Flag`，`flagCount = mineCount`），
  动画只是把它画出来。

### 1.4 扫描条裁剪（修复前后对比）—— 这是本轮改掉的那个真差异

| | 修复前（5557，旧包） | 修复后（5555，新包 66e6c33） |
| --- | --- | --- |
| 证据图 | `docs\verify\ANIM_win_00.jpeg` | `docs\verify\ANIM_win_00.jpeg`（同一批文件里，按设备分） |
| 条的高光带位置 | y = **522** | y = **522** |
| 棋盘上沿 | y = **540** | y = **289** |
| 条相对棋盘 | **在棋盘外 18 px**（停在棋盘顶上，不消失） | **在棋盘内 233 px**（被裁在棋盘里，扫到顶整条消失） |
| 匹配相似度 | 0.978 | 0.990 |

原版（`linux-minesweeper`，`BoardWidget::drawScanBar`）里是
`p.setClipRect(m_grid)` —— 扫描条**裁在棋盘矩形内**，扫到顶端就整个消失。
修复前我们是整条直接画，于是 p=1 时条停在棋盘上沿外面不走。
修复后 `Anim.scanBarRect()` 负责裁剪，`GameController.drawScanBar()` 只负责取矩形并画。

顺带修掉了条的高度：原来写死 `barH = 62 * unit`（9×9、unit=10 时是 620px），
跟源精灵 275:62 的比例对不上，条被拉扁；原版是
`barH = grid.width() * src.height() / src.width()`（= 1620×62/275 = 365px）。

### 1.5 爆炸动画会在踩雷格上播

| 证据 | 爆炸帧号 | 相似度 |
| --- | --- | --- |
| `docs\verify\ANIM_explode_00.jpeg`（绿盘，踩雷格 r=6,c=2） | **第 7 帧** | 0.925 |
| `docs\verify\ANIM_boom_d15_00.jpeg`（绿盘，踩雷格 r=0,c=4） | **第 10 帧** | 0.922 |

判定方法：爆炸精灵（`otherSheet` 逻辑坐标 `[728 + 59*(f%3), 59*(f/3), 57, 57]`，共 23 帧）
画在格子左上角 `(-18,-18)*unit` 处、边长 `57*unit`。
**整块去比是不行的** —— 精灵大半是透明的，周围棋盘像素会把相似度压到 0.48~0.73。
正确做法是：先用「橙红」判据（r>140 且 b<130 且 r-b>60 且 r-g>30）把火球找出来，
再拿**精灵里不透明的那些像素**去比。
帧号是这么认出来的，不是靠肉眼数。

截图里能直接看见火球：`ANIM_explode_00.jpeg` 第 6 行第 2 列是一个橙白色火球，
同一张图里其它雷格是静态的灰色雷精灵 —— 只有踩到的那一格在炸。

## 二、已确证、但与原版仍有差异

### 2.1 扫描条的高度/裁剪 —— 已修（见 1.4）

已合入 `66e6c33`。

### 2.2 爆炸动画的总时长 —— 已修

原来 `Anim.tick()` 是**按帧计数**推进的（每 tick 帧号 +1，而 tick 间隔是 30ms），
于是 23 帧只跑了 23×30 = **690ms**，比原版 `animationMineSweeper_MineTrip.xml`
的 **1 秒**短了三分之一。`EXPLODE_FRAME_MS` 这个常量当时是**死代码**。
现在改成按时间推进（`Anim.tripElapsed`），实测总时长 = 1000ms，与原版一致。

### 2.3 胜利动画的结束时刻 —— 已修

原来写死 `SWEEP_MS + DISARM_FRAME_MS * DISARM_FRAMES = 5000ms`。
但光束是在**扫描条扫到那一行**才开始放的 —— 雷落在最后几行时，
最后一束光束要到 3000ms 之后才开始，5000ms 会把光束**砍掉一半**。
原版是 `m_winEnd = max(3000, lastBeamStart + 2000)`。
现在 `Anim.winEndMs()` 就是这个式子。
> 实际影响：原来胜利对话框会晚 646ms 到 3000ms 弹出（取决于雷的行位置），
> 现在跟原版一致。

### 2.4 扫描条与拆雷光束的起跳时刻公式 —— 数学上等价，但写法不同

原版：`startMs = SWEEP_MS * (rows - r) / (rows + 1)`（条扫到第 r 行时那一行开始拆雷）。
我们：底部 3 行钳到 0，其余按条到达该行的时刻算。
实测两者相差 0.00ms，**行为等价**，可以不改。

### 2.5 胜利对话框的按钮文案 —— 仍未确证

用户已确认「Win7 判负确实弹对话框」，但**按钮文案**至今没有确证。
本轮截图里 `ANIM_win_02.jpeg` 之后画面就静止了，对话框已弹出，
但没有单独截到它的清晰特写。**这一条仍算「未确证」。**

## 三、尚未抓到 / 工具链的物理限制

### 3.1 爆炸动画的多帧连拍 —— 抓不动，是工具链限制

设备端实测延迟：

| 操作 | 实测 |
| --- | --- |
| `hdc shell uitest uiInput click X Y` | **485 ms** |
| `hdc shell snapshot_display -f x.jpeg` | **497 ms** |
| `hdc file recv` | 226 ms |

也就是说「点下去 → 第一张截图被拍下」最少要 **~1 秒**，
而爆炸窗口只有 **1 秒**（原版时长）。
**一次连拍最多压住 1 帧**，这是快门比动画窗口还慢造成的物理限制，
不是动画实现的问题。

对策与实测结果：给脚本加了 `--first-delay`（点击之后到第一张截图之间等多久），
用不同的延时**扫落点**，每轮落在不同的爆炸帧上：

| 延时 | 落到的爆炸帧 |
| --- | --- |
| 0.15 s | **第 10 帧**（相似度 0.922） |
| 0.30 / 0.45 / 0.60 s | 抓不到（已经过了爆炸窗口） |
| （另一轮，绿盘） | **第 7 帧**（相似度 0.925） |

已经拿到 **2 个不同的帧号**，足以证明**帧号在往前走**（7 → 10）。
要把 23 帧全部凑齐，需要能在 ~200ms 内连续取 23 张图，
本机设备端做不到（没有 `screenrecord` 可用）。

### 3.2 胜利动画的连拍帧率

胜利动画全程 3s（扫描）+ 2s（光束），连拍每帧 ~720ms，
所以一轮 20 帧里**只有前 2~3 帧是动画帧**，后面都是静止的终局画面。
这跟 3.1 是同一个限制。扫描条「在动」这件事是靠**帧间像素差**和
**高光带模板匹配的 y 坐标**证明的，不是靠连拍密度。

## 四、方法（可复现）

### 4.1 工具

| 文件 | 作用 |
| --- | --- |
| `tools\win_probe.py` | 真机自动解盘 + 连拍。`--phase win` 赢一局并连拍胜利动画；`--phase explode` 故意踩雷并连拍爆炸动画；`--first-delay` 控制爆炸的落点；`--tag` 改输出前缀 |
| `tools\anim_analyze.py` | 离线判定：扫描条位置（在不在棋盘内）、拆雷光束、爆炸帧号、帧间像素差 |

### 4.2 关键命令

```
# 胜利路径（5555）
python tools\win_probe.py --device 127.0.0.1:5555 --phase win --burst 20 --burst-gap 0.04

# 爆炸路径（扫落点）
python tools\win_probe.py --device 127.0.0.1:5555 --phase explode --burst 3 --burst-gap 0.02 --first-delay 0.15 --tag ANIM_boom_d15

# 离线判定
python tools\anim_analyze.py win  "docs\verify\ANIM_win_"  296 289 180 10 9 9
python tools\anim_analyze.py boom "docs\verify\ANIM_boom_" 296 289 180 10 9 9
```

### 4.3 自动解盘是怎么做到的

1. **找棋盘**：不用颜色包围盒（桌面的壁纸花纹也是规则网格，实测误判成 8×8 假网格）。
   改用**深色缝梳状滤波**找规则网格，再用 hilog 的版式信息**校验**：
   网格原点与 hilog 的棋盘原点只差一个状态栏偏移（dx ∈ [-12, 40]，dy ∈ [0, 320]），
   且网格尺寸乘格边之后放得进画布。
2. **认数字**：状态条计数器是七段数码管，但**棋盘上的数字仍来自精灵图**，
   蓝盘和绿盘的数字掩码逐位相同（8 个数字全验过），所以一套模板通吃。
   认格子时先看「淡色地板占比」区分「未揭开的方砖」和「已揭开的格子」。
3. **推理**：约束传播（单格规则 + 子集规则），推不出确定安全的格子时用
   **约束子集枚举**估「是雷概率」，点概率最低的那个。
   > 注：最早写的是「穷举所有可行解」，9×9 上要跑 188 秒 CPU 还没完（组合爆炸），
   > 换成子集枚举后是 **1 毫秒**。
4. **判终局**：**雷都算出来了**（红旗 + 已露出的雷 == 雷数）才算终局。
   赢还是输**由动画本身分辨**（扫描条/光束 = 赢，爆炸 = 输）。
   > 注：不能只看「棋盘上有没有雷」—— 胜利时引擎给所有雷插旗，
   > 而拆雷光束的精灵自带一份该格的方砖副本，光束扫过时那一格看起来像「已揭开的雷」，
   > 很容易被误读成判负（第一轮就是这样误判的）。
