## 0. 目标与边界

**目标**：在华为 Pura X Max 上像素级复刻 Windows 7 扫雷，折叠/展开双屏自适应。自用，不上架。

**明确不做**：

| 项 | 原因 |
|---|---|
| 系统标题栏 / 窗口边框 / 最小化按钮 | 手机没有窗口管理器，由系统提供 |
| 菜单栏（游戏/帮助） | V3 再补，不影响核心玩法 |
| 笑脸按钮 | **没有**（Win7 状态条左端是时钟；笑脸是 XP 的行为。**2026-10-31 用户本人确认 Win7 没有笑脸**，见 §5.5、§8 第 1 条） |
| 统计信息窗口 | **有**（`游戏 → 最佳成绩` 打开的是独立的「扫雷统计信息」窗口，不是小对话框，见 §5.8） |
| 新局发牌动画 | **有**（整盘先压平，方砖从四角波浪式弹起，1100ms，见 §5.9） |
| 洪泛涟漪 | **有**（展开的格子按切比雪夫方环分层淡入：每圈 30ms、单格 150ms，见 §5.9） |
| 胜利扫描条 + 拆雷光束 | **有**（扫描条 3 秒自下而上 + 38 帧拆雷光束，扫完才弹框，见 §5.9） |

**保留**：棋盘、渐变砖块、数字、旗/问号/红叉/雷、上下状态条（雷数 + 图标、计时 + 时钟图标）、胜负对话框的像素与文案。

## 2. 尺寸与难度

| 难度 | 行 × 列 | 雷 |
|---|---|---|
| 初级 | 9 × 9 | 10 |
| 中级 | 16 × 16 | 40 |
| 高级 | 16 × 30 | 99 |
| 自定义 | 9–24 行 × 9–30 列 | 10–668（面板上限） |

引擎层的每尺寸雷数上限：`maxMinesFor(r, c) = (r-1)*(c-1)+1`
（24×30 → 668，与面板上限吻合；该值同时保证剩余空格 ≥ r+c-1，够放首点 3×3 安全区。）

自定义局**不计入统计/排行榜**（原版如此）。

## 3. 规则（逐条）

### 3.1 延迟布雷 + 首点 3×3 安全区

按下左键之前棋盘上没有雷。第一次左键点开某格时才布雷，且**排除该格及其周围 8 格（越界裁剪）**。

结果：首点必定打开一片空地（"根据地"），而不是只保证不炸。角落首点至少开 4 格，中心至少 9 格。

### 3.2 左键开格

开到的格子周围雷数为 0 时，广度优先连锁展开（洪泛）。
- 洪泛**不**自动打开插旗格
- 打开的问号格会被清成空格
- 用 BFS 而非递归：高级局一片空地可能上千格，递归会爆栈
- 展开顺序按 BFS，UI 照此播放扩散动画

### 3.3 右键三态

无标记 → 旗 → 问号 → 无标记。问号可在选项里关掉（关了就是 旗 ↔ 无标记 两态）。

插旗时剩余雷数 −1，取消时 +1，**可以为负**。

### 3.4 和弦

在已打开的数字格上，若周围旗数 == 该数字，则一次性打开周围所有未插旗的格。

- 旗数不等于数字：什么都不发生
- **旗插错时：周围所有未被正确标记的雷同时引爆，直接判负**

### 3.5 失败展示

- 所有未插旗的雷显示为黑雷
- 被踩中的那颗显示为**红底雷**
- 用户插错旗的非雷格，旗子上叠**红叉**
- 表情（如果有）变哭脸 —— 是否有表情尚未定论，见 §8 待确认项 1

### 3.6 胜利

- 剩余未插旗的雷**自动变成旗**
- 剩余雷数归零
- 计时停止

### 3.7 计时

- 第一次左键**松开**时才开始，先置 1 再启动 1 秒 tick（引擎侧：第一次 reveal 触发 `Ready → Playing`）
- 上限 999，到顶不回绕
- 最小化 / 失焦时暂停

### 5.2 砖块渐变（还原原版质感的关键）

原版不是所有格子同一个蓝色，而是 720 帧（30×24 最大棋盘每格一帧）从左上到右下由亮到暗的渐变，每格取自己那一帧。小棋盘取**居中窗口**而不是拉伸整个渐变：

```
r = min(23, row + max(0, (24 - rows) / 2))
c = min(29, col + max(0, (30 - cols) / 2))
frame = r * 30 + c
```

不这么做，9×9 初级局会显得过亮或过暗，和原版对不上。

### 5.3 缩放档位（像素级的硬约束）

素材是 2 倍图，源一格 = 36 存储像素。**要像素锐利，格子的设备像素数必须是 36 的整数倍**，否则缩放插值会把边缘弄糊。

设设备密度 density（px per vp，Pura X Max 约 2.625，对应 420dpi 档）：

| 档位 n | 格子设备像素 | 格子尺寸(vp) | 物理尺寸 | 30 列棋盘宽(vp) |
|---|---|---|---|---|
| 1 | 36 | 13.7 | ≈2.2 mm | 411 |
| 2 | 72 | 27.4 | ≈4.4 mm | 822 |
| 3 | 108 | 41.1 | ≈6.7 mm | 1234 |
| 4 | 144 | 54.9 | ≈8.9 mm | 1645 |

画布必须 `imageSmoothingEnabled = false`（最近邻），否则不是像素级。

#### 适配档的计算口径（2026-10-31 修订，来源 `docs\LAYOUT-MATRIX.md`）

「整盘刚好放下」的档位 `fit` **只按真正画出来的东西算**：

```
横向预算：棋盘宽 = 列数 × 18 × 2n
纵向预算：菜单栏高 + 棋盘高 + 状态条带(32×2n)
```

修订前算的是「棋盘 + 原版玻璃边框留白（左右 59、上下 62 个参考单位）」。手机版**不画那个边框**
（`drawBoardArea()` 只在棋盘矩形内填白地板加三边 1px 凹槽线），那 59/62 单位纯属白占缩放预算，
把高级/中级局在窄屏上压到 n=1（格边 10~13 vp，手指根本点不准）。实测效果（Mate X7 模拟器）：

| 画布 | 难度 | 修订前 | 修订后 | 棋盘宽度占比 |
|---|---|---|---|---|
| 2210×2208 | 初级 9×9 | n=4（格边 144） | **n=5（格边 180）** | 58.6% → 73.3% |
| 2210×2208 | 高级 16×30 | n=1（格边 36） | **n=2（格边 72）** | 48.9% → 97.7% |

配套两条：
- **棋盘 + 状态条这一组在菜单栏以下的区域居中**（菜单栏进竖向预算，不再「恰好没碰上」）。
- **放得下时不允许平移**（原来 `clampPan` 用 `|(画布-底板)/2|`，初级局能把棋盘拖偏几百像素）。

#### 最小可点格边 48px：装得下但点不准就抬一档（2026-10-31 13:39 加）

30 列的局在窄屏上宽度是**几何必然**装不下。装得下的那一档格边只有 36 设备像素
（≈10~13 vp），手指根本点不准。**这时宁可让棋盘横向超出画布（靠平移看），也不要给一个点不中的棋盘。**

规则（``GameController.layout()``）：

```
若 36 × 2 × fit < MIN_CELL_PX 且 fit < MAX_SCALE_INDEX：
    抬到 fit+1 的那一档，若「抬完纵向仍装得下」或「横向本来就装不下」，才真的 fit = fit + 1
```

常量 `MIN_CELL_PX = 48`（``Theme.MIN_CELL_PX``，48 px 是经典的最小点按目标尺寸）。

**「不能无条件抬」**：抬档会让棋盘同时纵向溢出，而纵向若用**居中**，
棋盘顶部会被推到菜单栏底下 —— 那几行既看不见也点不着（菜单栏的点击归菜单）。
所以抬档的前提是「抬完纵向仍然装得下」，或者「横向本来就装不下」
（反正要平移，纵向溢出无所谓，只需**顶对齐**）。
纵向对齐因此也分两种（``GameController.applyGeometry()``）：

```
frameH > 可用高度  →  顶对齐（frameY = 菜单栏下沿），把溢出全放到下面
否则              →  在菜单栏以下的剩余空间里居中
```

以上两条是 2026-10-31 13:51 补的，依据是 `docs\LEAD-CHANGE-AUDIT.md` 的 **L1 [HIGH]**；
已随 commit `9a70112` 提交。

#### 对话框的高度也要封顶（2026-10-31，commit `9a70112`）

`computeDialogScale()` 原来只按**宽度**封顶，短画布（横屏、分屏）上对话框会**超出屏幕高度**，
底部按钮跑到屏幕外点不到。实测例：900×400 画布 @密度 2.75，
396×340 的胜利框 ×2 = 792×680，按钮全在屏外。

现在宽度与高度都参与封顶（``GameController.computeDialogScale()``）：

```
s = max(0.5, min(2, density, (canvasW - 32) / refWidth, (canvasH - 32) / refHeight))
```

并且对话框比画布还高时**顶对齐**（``GameController.dialogLayout()``），不再居中
（居中会让上下各露一半，底部按钮够不着）—— 这是 `LEAD-CHANGE-AUDIT` 的 **L4**。

依据是用户原话：「**外屏不接受降级，我希望可以拖动放大**」。

> `docs\LAYOUT-MATRIX.md` v2.0 的数据快照是 13:35，本规则是 13:39 才加的，
> 所以 v2.0 表里「窄屏 + 高级 16×30 = n=1（格边 36）」那几行**已过期**：
> 按当前代码会抬到 **n=2（格边 72）**。要拿与当前代码一致的数字，重跑 `tools\check_layout.py`。

#### 整数像素落点（2026-10-31）

`v(px)` 原来直接 `px * pxScale`，落在**分数设备像素**上的矩形与文字会被抗锯齿糊掉
（对话框的缩放是小数，按钮、文字全在半像素上）。像素级复刻要求边缘锐利，所以改成**先取整再换算**
（``GameController.v()``）：

```
v(px) = Math.round(px) * pxScale
```

#### 布局日志的字段（2026-11-01）

每次重新布局（画布尺寸变化、折叠换屏、画布重建）都会打一行：

```
[GameController] 布局 画布=<宽>x<高>px 密度换算=<pxScale> 适配档n=<n> 当前档n=<n> unit=<u> 格边=<px>px 棋盘原点=(<x>,<y>) HUD=<0|1> 状态条上沿=<px>px 盘面=<行>x<列> 雷=<数>
```

| 字段 | 含义 | 设备无关 |
|---|---|---|
| `画布=` / `密度换算=` | 画布尺寸与 vp → 设备像素的换算系数 | 否（随设备与姿态变） |
| `适配档n=` | 「整盘刚好放下」所需的档位（程序自己算的） | 否 |
| `当前档n=` | 现在实际用的档位，**捏合改的就是它** | 否 |
| `unit=` / `格边=` | 每逻辑单位的设备像素数 / 一格的边长 | 否 |
| `棋盘原点=` | 棋盘左上角在画布里的位置（**负数是正常的**，表示超出屏幕左边） | 否 |
| `HUD=` | 1 = 状态条被钉在画布底边（纵向装不下时） | 否 |
| `状态条上沿=` | 状态条带的顶边 y | 否 |
| **`盘面=<行>x<列>`** | **这局棋多大** | **是** |
| **`雷=<数>`** | **这局有多少个雷** | **是** |

> **为什么加了 `盘面=` 与 `雷=`**（2026-11-01，Codex 复审 P2）

> 格边和原点是**随设备变**的 —— 两台模拟器的画布尺寸不同，真机又是另一套，
> 把它们写死当断言，就会在别的设备上**假失败**。
> `盘面` 与 `雷` 是**盘面本身**的属性，不随屏幕尺寸变，
> 所以断言「有没有真的开出了 24×30 这一局」要看这两个，**不要**看格边和原点。

> 同理，**捏合缩放不会另外打日志**（`zoomTo()` 不打任何日志），
> 想看捏到了第几档，只能靠折叠触发一次重新布局、再读这一行的 `当前档n=`。

#### 对话框缩放统一（2026-10-31）

结束对话框、统计窗口、自定义难度框三者的缩放统一走 `GameController.computeDialogScale(refWidth, refHeight)`
（``GameController.computeDialogScale()``），按**物理密度**算、保证放得下、**封顶 2 倍**：

```
s = max(1, min(2, density, (canvasW - 32) / refWidth))
```

调用点：``GameController.computeDialogScale()``（结束框）、`:1180`（统计窗）、`:1281`（自定义框）。
自定义框此前一直用**陈旧初值 1**，在 Mate X7 内屏上只有约 260×190 设备像素（正文约 2.7 vp，

### 5.4 地板与黑边（2026-10-30 实测修订）

**地板**：翻开的格子不是白色，而是该格的「**按下态**」渐变砖块（`normalTileRect(frame)` 的 x 加 500）——那是一块浅灰的扁平砖。原版窗口底图（`Frame.bmp`）里的白色只是空棋盘时的窗口底色，铺满砖块后看不见。

**黑边**：凸起的格子向**下和右**投出黑边（素材 `RECT_SHADOW_U` / `RECT_SHADOW_L` 是不透明黑，不是半透明）：

- 上方（或首行）有凸起格 → 地板格上沿画 3 单位高的黑条
- 左方（或首列）有凸起格 → 地板格左沿画 3 单位宽的黑条
- 两者都有 → 竖条从横条下方开始画，角落不重复加深

`docs\STATUS-STRIP-VERDICT.md` 结论 A：

- 素材层：Win7 的精灵表里与状态条有关的**只有两个 25×25 面板图标**

  全套素材的「黄色圆盘」扫描结果是 0（`otherSheet` 里的暖色像素是爆炸火球与花朵）。

  `linux-minesweeper/src/ui/BoardWidget.cpp:522-525` 明说布局照的是原版 MINESWEEPER.xml CustomLayout。
- 交互层：Win7 保真复刻的 `BoardWidget.cpp:783-813` **只对棋盘格做命中测试**，
  棋盘外的点击（包括状态条）一律忽略。**原版点这两个圆钮没有任何反应。**

→ 所以「点不动」是**正确行为**。「点时钟重开」若要做，属于我们自己加的易用性功能，
**不是复刻**，不应写进「与 Win7 一致」的清单里。项目已有 F2 与菜单「新建」两条正路。

#### 局终关框后点棋盘 = 重开一局（2026-11-04 新增，**属于增强，不是复刻**）

**行为**：判负/判胜的结算框关掉之后，再点棋盘任意一格 → **同盘面重开一局**
（`GameController.tap()` 里 `gameState` 是 `Won`/`Lost` 时走 `restart()`，
盘面、难度、自定义局标记都保持不变，跟「再来一局」按钮同一条路）。

**原版不是这样**：Win7 局终之后棋盘是**锁死**的 ——
Win7 保真复刻 `linux-minesweeper/src/ui/BoardWidget.cpp:783-793` 写得很直白：

```cpp
if (m_board->over()) {
    finishExplosionNow();
    finishWinNow();
    return;                 // 这次点击被吃掉，不会开格
}
```

**为什么加**：2026-11-04 用户反馈「关掉结算弹窗之后再点棋盘，界面一点反应都没有」。
局终后棋盘是死的，而状态条上又**没有笑脸按钮**（Win7 确实没有，见上一节），
于是在**不碰菜单**的前提下没有第二条路重开 —— 容易被当成应用卡住了。
点了就重开，语义直白，也和弹窗上的「再来一局」一致。

**口径**：这是**自加的易用性功能**，按 §7 第 7 条的规矩，
**不能**写进「与 Win7 一致」的清单，必须标成增强。
证据与实测见 `docs\DEV-CHECKLIST.md` 的对应条目与
`docs\verify\CM_<tag>_board_restart_after_gameover.jpeg`。

### 5.7 HarmonyOS Canvas 的单位陷阱（2026-10-30 真机实测，务必知道）

这一节是本项目在 Pura X Max 上真机验证出来的**三个连环坑**，每一个都单独烧掉一次真机往返：

| 坑 | 现象 | 真相 | 正确做法 |
|---|---|---|---|
| **坐标单位是 vp** | 按设备像素算好的棋盘跑到右下角、尺寸溢出 | Canvas 的绘制坐标单位是 **vp**（1 单位 = 1 设备像素 / density） | 内部按设备像素算（格边必须落在整数像素上），**送进 Canvas 前统一乘 `1/density`** |
| **PixelMap 源矩形也是 vp** | 格子只画出 1/3 大、图块错位像楼梯 | SDK 原文：PixelMap 源的裁剪矩形 (sx,sy,sw,sh) 在 **API 18 起默认单位是 vp**（更早才是 px） | **源矩形也要乘 `1/density`**，否则等于从图集里裁错区域 |
| **onReady 的参数不是 DrawingRenderingContext** | 一启动就崩：`param is not a DrawingRenderingContext object` | 类型声明说是 `DrawingRenderingContext`，**运行时给的其实是构造 Canvas 时传进去的那个对象** | 构造时传 `CanvasRenderingContext2D`，`onReady` 里就直接用它，**不要再桥接** |

补充：`errorManager` 的事件名在 API 26 是 `'globalErrorOccurred'`（不是老版本的 `'error'`），回调参数是 `GlobalError`（继承 `Error`，有 `message`/`stack`），不是 `BusinessError`。

**教训**：本节所有结论都来自 SDK 的 `.d.ts` 与注释，**不是凭记忆**。下回写任何 ArkUI API 之前，先在 SDK 里搜一遍声明：

```
Select-String -Path 'D:\software\DevEco Studio\sdk\default\openharmony\ets\build-tools\ets-loader\declarations\*.d.ts' -Pattern 'xxx'
```

**以及**：真机跑不起来时，用 `errorManager.on('globalErrorOccurred', ...)` 把异常抓出来（配 `console.error`），比猜快得多。

**本项目的处理**：手机上不画原版那圈玻璃窗口边框（手机没有窗口管理器），改为：底色 + 白色地板 + 左/右/下三边 1px 凹槽线（实测 rgb(76,85,111)）。原版 30 列窗口里白色棋盘区实测为 x=30..570、y=30..318。

> 已定（2026-10-30）：`Frame.bmp` **不用作九宫格底板**。原版那圈玻璃边框属于系统窗口外观，手机上没有窗口管理器；棋盘区改为自绘地板 + 凹槽线。见 §5.6。

### 5.8d 对话框的逐像素比对（2026-10-31）

### 5.9 三段动画（发牌 / 洪泛涟漪 / 终局）

三段的顺序与节奏全部有出处，注释写在 `DealIn.ets` / `Ripple.ets` / `Anim.ets` 的文件头。

| 动画 | 参数 | 依据 |
|---|---|---|
| **新局发牌** | 整盘先画成压平的浅色底砖，方砖从四角波浪式弹起，**总时长 1100ms** | Lmy `Minesweeper.cpp:1496-1508`（`speed(1100/(row*col))` 逐格延时）+ `core.h` 的 `getFirstPaintNo()` 顺序 |
| **洪泛涟漪** | 按**切比雪夫方环**分层，**每圈 30ms**，单格 **150ms** 线性淡入；展开格数 **<6 不涟漪** | Qt 复刻 `BoardWidget.cpp:22/30/31`（`kTickMs=30`、`kRippleStagger`、`kRippleFadeTicks=150/30`）、`:283` 的 `qMax(qAbs(dx),qAbs(dy))`、`:271` 的 `order.size()<6` |
| **踩雷爆炸** | 23 帧 / 1 秒，帧矩形 `(728+59*(f%3), 59*(f/3), 57, 57)`，偏移 (−18,−18)；**判负是冲击波级联**：踩中的那颗 0ms 起炸，其余未插旗的雷按到中心的格距 `round(距离×5)×30ms` 依次起炸，插了旗的雷不炸；还没轮到的那颗**仍盖在凸起砖下面** | Qt `Theme.h` 的 `tripFrame()`（来自原版 `animationMineSweeper_MineTrip.xml`）；级联依据 Qt `BoardWidget.cpp:167-206`（`kRingStagger` 按 30ms 时钟步长）、`:641-645`（未轮到的雷盖在砖下）、`:679`（花园的花开完才出现） |
| **胜利扫描条** | 扫描条 3 秒自下而上，横向拉伸到棋盘宽；扫到某行时该行的雷播放 38 帧 / 2 秒的拆雷光束；**全部放完才弹胜利框** | Qt `Theme.h` 的 `kScanBar{0,912,275,62}` 与 `disarmFrame()`（原版 `animationMinesweeper_MineDisarm.xml`） |
| **拆雷光束的起跳时刻** | **按行号均匀分配**：`startMs = round(3000 × (行数 − r) / (行数 + 1))`（9 行盘 = 300…2700ms 依次亮），**不是**按扫描条的真实高度几何算 —— 几何算法会让最底几行在 0ms 同时开火 | Qt `BoardWidget.cpp:244` 的 `kScanTicks*(rows-r)/(rows+1)`（参照实现自述取自原版 UI XML）；差异与裁决见 `docs/ANIM-PARITY.md` §五 |

**性能约定**：四段动画共用**一个 30ms 帧定时器**（`GameController.tickFrames`），每帧只重画一次。
早先每个动画各开一个 `setInterval`，重叠时同一帧会把整块画布画三遍，折叠屏上会掉帧。

**与 2026-10-31 版式重做的关系**：版式重做（§5.3）改了棋盘原点与底板尺寸，
所以四段动画的落点一律**跟着棋盘矩形走**，不写死坐标 ——

（commit `b66208b` 修过一次「行程算多了一倍条高，p=1 时会扫过棋盘顶」）；
画布重建（折叠/旋转）时待弹的结束框标记与进行中的动画都要保住
（commit `96f4f57`，Codex 复审 P1 两条）。

## 6. 交互规格（手机重设计）

原版是鼠标三键（左开格 / 右标记 / 中键和弦），手机上不存在，必须重映射：

| 原版 | 手机 | 说明 |
|---|---|---|
| 左键 | 单击 | 开格 |
| 右键 | 长按（≥400ms） | 插旗 / 问号 / 取消，循环同右键 |
| 右键（选项） | 长按循环或旗子模式开关 | 二选一，见下 |
| 中键 / 左右同按 | 双击已翻开的数字 | 和弦 |
| 鼠标悬停高亮 | 按下高亮 | 素材里高亮帧是**相加混合** |
| 滚轮 / 拖窗口 | 双指缩放 + 单指拖动 | 见 §7 |

**手势仲裁**（同一片区域上三个手势）：

- 单击判定：位移 < 10vp 且时长 < 300ms
- 长按判定：按住 ≥ 400ms 且位移 < 10vp
- 拖动判定：位移 ≥ 10vp（此时取消单击与长按）
- 双击：两次点击间隔 < 300ms，且都未触发拖动
- 双指捏合：缩放，松手**吸附到最近的整数档位 n**

**和弦在手机上是刚需**，不是可选：高级局不开和弦基本没法玩。

| 外屏 · 中级 16×16 | n=2 | 439 × 439 | 704 × 481 | 纵向差一点 |
| 外屏 · 高级 16×30 | n=3 | 1234 × 658 | 704 × 481 | 双向 |

外屏高级必须平移，这是物理决定的（30 列 × 2.2mm 的格子点不准）。**代价**：视野受限，扫雷依赖全局信息（哪片区域安全），体验会变累。可选补偿：加一个"全览缩略图"或"回到全览"按钮。

### 7.4 折叠保活

游戏状态必须放在 **Ability 级单例 / AppStorage**，不能放在页面组件的 `@State` 里——折叠展开会重建页面，状态会丢。同一份状态要能在内屏、外屏之间原样迁移（雷位、旗、计时、当前缩放档位与视口中心）。

## 11. 2026-10-31 这一轮做了什么

### 11.1 修掉的两个"点不动"的 bug（都是 ArkUI 命中测试的坑）

| 现象 | 根因 | 修法 |
|---|---|---|
| 菜单打开后条目点不动 | `hitTestBehavior(HitTestMode.Block)` 加在**容器**上时，API 26 下它自己的子组件（`Text`/`Button` 的 `onClick`）收不到点击 | 容器**不设** Block；改为「菜单打开时锁住棋盘输入」（`controller.inputLocked`），面板外不再铺全屏遮罩 |
| 结算面板按钮点不动 | 同上 | 同上 |

**教训（写进 §5.7 同级）**：`HitTestMode.Block` 只能用在**叶子/无子组件**的覆盖层上；给容器加 Block 会连自己的儿子一起"打死"。
全屏遮罩还会和面板里的条目**抢同一次点击**，条目随机失灵——所以不要用遮罩，用输入锁。

### 11.2 M3 缩放与平移

- 缩放档位 n ∈ [1,8]（每格 36…288 设备像素，始终是素材 36px 的整数倍，最近邻不糊）。
- **双指捏合**：以两指中点为锚点缩放，吸附到整数档；中点位移同时驱动平移。
- **单指拖动**：位移 ≥ 10vp 判定为拖动 → 平移棋盘（此时取消单击与长按）。
- 平移夹紧：棋盘不能被拖出画布；整盘放得下时平移量强制归零。
- 新局回到「整盘刚好放下」的档位（`fitScaleIndex`）；用户手动缩放过就保留（折叠换屏不丢视角）。

### 11.3 M4 折叠屏

- 画布尺寸变化由 `onAreaChange` → `attach()` → `layout()` 全链路自动重排（**没有**用 foldStatus 做布局）。
- 游戏状态在 `GameSession` 单例里，页面重建（折叠/旋转）不丢局。
- 切后台暂停计时，回前台恢复（手机上放口袋不该继续耗秒数）。

### 11.5 音效（原版 Win7 素材）

直接用 `win7-assets/audio` 里的微软原版 wav，已复制到 `rawfile`：
`firstPaint`（**发牌动画配乐**）/ `gameStart`（新局事件音，暂未接线）/ `gameWin` / `gameLose`（**逐雷各一声**）/ `tileSingle` / `tileMultiple` / `invalidMove`（**和弦失败**）/ `dbButtonClickFlag` / `mineBombStart` / `mineBombRun` / `mineBombEnd` / `zeroDevelop`；
外加花园判负三段 `flowerLoseShort / flowerLoseMedium / flowerLoseLong`，共 **15 个**。

播放用 `resourceManager.getRawFd()` → `AVPlayer.fdSrc`，免去把文件复制到沙箱目录。爆炸是三段连播（间隔 260ms）。

**2026-11-01 的素材与接线审计**（`docs/SOUND-AUDIT.md`）：

- **15 个 wav 与原版逐字节相同**（sha256 全等，44100 Hz / 16 bit），没有改过任何一个。
- 修了四处接线问题：
  1. **和弦失败没声音**（P1）：点已翻开的数字格、周围旗数 ≠ 数字时，原来一声不响 ——
     `invalidMove.wav` 在正常玩法里永远不响。现在响了（Linux 复刻 `BoardWidget.cpp:840`、
     Lmy 克隆 `Minesweeper.cpp:1357-1359` 都响）。
  2. **花园玩法叠了 4 条声**（P1）：花园判负时爆炸三段与枯萎声一起响。
     原版的花园模式 `mineTripped()` 直接 return（Linux 复刻 `Sounds.h:71`），只有枯萎声。
     现在花园**不播**爆炸三段。
  3. **终局后点棋盘会响**（P2）：结束框点「换个难度(D)」关掉框后棋局仍是终局，
     这时再点空格每点一声 `invalidMove`。现在只在**还在玩**的时候响。
  4. **长按已翻开的格子也响插旗音**（P2）：`toggleMark()` 的返回值被丢掉了，
     引擎在「已翻开 / 终局」时返回 false —— 现在只在真的插上旗时才响。
- **花园判负分档用「本局总雷数」**（≤10 Short / ≤40 Medium / 其余 Long），
  不是剩余雷数（判负前玩家往往已插 30 面旗，用剩余数会整档错位）。
  参照实现喂的是「待爆雷数」，两者在插旗多时会差一档 —— 口径**以本项目既定裁决为准**（总雷数）。
- 爆炸结束音现在跟着**级联长度**走（`Anim.tripEndMs()`），放结束音前先停掉爆炸中音
  （原版是先停循环再放结束音）；`SoundPlayer` 补了 `stop(name)`。
