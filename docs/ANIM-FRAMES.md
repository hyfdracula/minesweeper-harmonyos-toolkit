| 爆炸 `ANIMF_exp_x15_c1` | 2 → 4 → 5 → 6 → 8 → 9 → 11 → 13 → 14 → 17 → 19 |
| 爆炸 `ANIMF_exp_x25_c?` | 5 → 6 → 8 → 10 → 11 → 13 → 14 → 17 → 19 |
| 开花 `ANIMF_flo_d0_c0` | 3 → 9 → 17 |
| 开花 `ANIMF_flo_d35_c1` | 2 → 8 → 14 → 19 |
| 开花 `ANIMF_flo_d70_c1` | 4 → 10 → 17 → 22 |

| 开花 `ANIMF_flo_d140_c0` | 6 → 12 → 19 |

**帧号随着时间单调递增，且两轮之间「延时越大、起始帧号越大」也对得上**

这说明**帧号不是认错的**：认错的话帧号不会随时间单调走。

## 二、慢放：只是取证手段，发布包仍是原版的 1 秒

### 2.1 为什么需要慢放

设备端实测：

| 操作 | 实测耗时 |
| --- | --- |
| `hdc shell uitest uiInput click X Y` | 485 ms |
| `hdc shell snapshot_display -f x.jpeg` | 497 ms |
| `hdc file recv` | 226 ms |

**快门（≈1.5 s 一帧）比原版 1 秒的爆炸窗口还慢**，
所以在发布包里一次连拍最多压住 1 帧 —— 23 帧根本抓不齐
（这就是 `docs\ANIM-VERDICT.md` 里记的那条「工具链的物理限制」）。

取证时的做法：在 `Anim.ets` 里临时把爆炸的帧间隔乘一个倍率
（`EXPLODE_FRAME_MS * EXPLODE_SLOWMO`），慢放 8 倍后爆炸持续 8 秒，
快门就能连着抓好几帧。

### 2.2 慢放常量已复原

```ts
// entry/src/main/ets/common/Anim.ets
static readonly EXPLODE_SLOWMO: number = 1;
```

帧间隔 = `1000/23 * 1` = 43.478 ms，总时长 = `43.478 × 23` = **1000 ms**，
与原版 `animationMineSweeper_MineTrip.xml`（1 秒 / 23 帧）一致。

**运行时复核（发布包，已重装）**：

| 证据 | 结果 |
| --- | --- |
| `ANIMF_rel_par_*`（点击丢后台线程、立刻连拍） | 认到**第 6 帧**（相似度 0.927）、紧接着第 19 帧（0.878），第 3 帧就已经是动画结束的静止画面 —— 整个爆炸横跨约 1 秒 |
| `ANIMF_rel_0_*` / `ANIMF_rel_30_*` / `ANIMF_rel_45_*` / `ANIMF_rel_60_*`（第一张截图落在点击之后 1 秒开外） | **一帧都看不到**（相似度只有 0.836 的静止画面误认） |
| 对照：慢放包（8 倍）同样的第一张截图 | 还能看到第 1 帧（0.902） |

结论：**发布包的爆炸已经回到 1 秒**（慢放 8 倍时同样的取景点还能看到动画，
发布包里就看不到了 —— 这正是「恢复到 1 秒」的直接证据）。

引擎单测：`tools\run_engine_tests.ps1` → **41 passed / 0 failed**。

## 三、方法

### 3.1 工具：`tools\anim_frames.py`

一条命令干三件事：**在真机上故意踩雷并连拍 → 对每一帧做帧号标注 → 汇总成表**。

```
python tools\anim_frames.py --device 127.0.0.1:5555 --kind explode \
    --tag ANIMF_exp_x5 --burst 18 --device-burst --first-delay 0.05
python tools\anim_frames.py --device 127.0.0.1:5555 --kind flower \
    --tag ANIMF_flo_d0 --burst 12 --first-delay 0.0
```

| 参数 | 作用 |
| --- | --- |
| `--kind` | `explode`（扫雷爆炸）/ `flower`（花园开花）。**它同时决定应用该是哪种游戏样式** |
| `--style` | 目标样式，默认由 `--kind` 决定；显式给成与 `--kind` 矛盾的值会**直接报错退出（码 2）**，免得拿矿雷画面去匹配花朵帧 |
| `--switch` | 跑之前先把应用切到目标样式（菜单 → 游戏(G) → 颜色(C) → 缩略图 → 确定(O)） |
| `--burst N` | 连拍多少帧 |
| `--device-burst` | **设备端连拍**：一条 shell 命令在设备上连着跑 N 次 `snapshot_display`，文件先落在设备上；本机这边一边等一边取回。节奏从 1.5 s/帧提到 ≈0.5 s/帧 —— 这是能凑齐帧号的关键 |
| `--first-delay` | 点击之后到第一张截图之间等多久，用来**微调落点**（落在第几帧） |
| `--parallel` | 点击丢后台线程、立刻开始连拍（用来抢第 0 帧） |

退出码：`0` = 抓到了；`3` = 一帧都没抓到（summary 里 `"captured": 0`）；
`2` = 参数自相矛盾。summary 里带 `captured`、`frame_ids`、`cell`、`frames`。

### 3.2 帧号是怎么认出来的（不是肉眼数）

1. **定位格子**：踩雷格是推理确定的，坐标已知。
2. **裁出精灵区**：爆炸画在格子左上角 `(-18,-18)×unit` 处、边长 `57×unit`；
   开花画在 `(-9,-9)×unit` 处、边长 `36×unit`。
3. **只比精灵里不透明的像素**：`otherSheet` 里这两组精灵四周是透明的，
   拿整块去比会把周围棋盘像素算进去，相似度只有 0.48~0.73 —— 认不出来。
   用 `alpha >= 110` 的掩膜只比实心部分，相似度上到 0.85~0.97。
4. **取相似度最高的那一帧**作为帧号。

**误认要排除**：动画播完之后画面稳定下来，那一帧会和某一帧模板「有点像」
（爆炸约 0.836、开花约 0.891）。所以**只认相似度 ≥ 0.85 的帧**，
低于这个的一律不算数 —— 这也是脚本里 `captured` 的口径。

### 3.3 怎么保证踩到的是雷

用 `tools\win_probe.py` 里那套扫雷推理（约束传播 + 约束子集枚举）找出「必定是雷」的格子。
踩第一颗如果没炸（前 4 帧都不匹配），脚本自动换下一颗重试。

### 3.4 花园主题的读盘

花园主题下已揭开的雷格显示的是**雏菊**而不是雷精灵，所以读盘要单独做：
先用「淡色地板占比」区分未揭开的凸起砖，再用**黄心**（r>170 且 g>120 且 b<150）
认出已揭开的花雷，其余格子照常读数字。

### 3.5 切游戏样式

「游戏(G)」→「颜色(C)」→ 点缩略图 →「确定(O)」。
对话框几何全部按代码算（`Appearance.ets`：`DLG_W=420`、`DLG_H=340`；
`GameController.computeDialogScale`：`s = max(0.5, min(2, 1/pxScale, (canvasW-32)/420, (canvasH-32)/340))`），
所以脚本不依赖硬编码的绝对坐标。

## 四、没抓到的帧号与原因

| 动画 | 缺 | 原因 |
| --- | --- | --- |
| 爆炸 | 0、18、20、21、22 | 见下 |
| 开花 | 0、7、15、20 | 见下（**第 0 帧另有原因，见 §4.1**） |

**第 0 帧**：点击命令本身要 485ms（uitest 启动开销），手指落下就已经在这之后了；
第一张截图最快也在点击之后约 0.5 秒，慢放下每帧 348ms，**落点最早落在第 1 帧**。
`--parallel`（点击丢后台线程）能把落点往前推，但设备端 `snapshot_display` 的启动开销
（约 200~400ms）还是比一帧长，仍差一点。

### 4.1 花开的第 0 帧：**它是一张全透明的空图**，模板匹配原理上就认不出

这一条是 2026-11-01 查原版资源时查明的（见 `docs\ANIM-PARITY.md` §3.3）：

> 花园开花序列的第 0 帧，在 otherSheet.png 的逻辑坐标 `(905, 0, 36, 36)` 处，
> **36×36 区域内的不透明像素数 = 0** —— 整张精灵是全透明的空图。

把 23 帧连成联系表看就是：第 0 帧**什么都没有**，第 1 帧才是一粒芽，
然后 2~4 花苞张开、5 开出雏菊、6~22 稳定。

**这不是我们的 bug，原版资源本身就是这样**（我们画的也是这张空图，行为一致）。
但它有个取证上的后果：**空帧对任何模板都一样不像**，模板匹配永远不可能
把它「认」成第 0 帧（相似度会低于阈值，与它到底是第几帧无关）。
所以本文件里开花序列「缺第 0 帧」是**方法上的必然**，
不是快门慢、也不是动画没播第 0 帧 —— 就算快门快到 1ms，那一格仍然是空的。

（爆炸序列的第 0 帧**不是**空图：那里有 1764 个不透明像素，是一小撮火星，
所以它是可以被模板匹配认出来的；爆炸缺第 0 帧确实只是快门慢。）

**第 18/20/21/22 帧（爆炸）与 7/15/20 帧（开花）**：这些帧都在动画的**末尾**，
落点要求截图正好发生在那 1 秒里的特定瞬间。点击→截图的总延迟在实测中
有 ±0.5 秒的抖动（uitest 启动、hdc 连接建立、shell 循环启动各占一部分），
所以**没法精确控制落点**，只能一轮轮地撞。
已跑 20 多轮，爆炸撞到第 19 帧（`ANIMF_exp_x45_c0_10.jpeg`），
开花撞到第 22 帧（`ANIMF_flo_d70_c1_03.jpeg`），
再往后就是「截图落在动画结束之后」，只剩静止画面。

**这四条是设备端工具链的物理限制，不是动画实现的问题** ——
从「同一轮里帧号严格递增、且延时越大起始帧号越大」可以看得很清楚：
动画本身是在按时间一个帧一个帧往前走的，只是快门跟不上。

### 已按 Codex 复审意见修的两条 P2

1. **`--kind flower` 不再和 `--style` 脱节**：`--kind` 现在**直接决定**游戏样式
   （`explode`→`mines`，`flower`→`flower`），`--style` 只是覆盖项，
   显式给成矛盾值会**报错退出（码 2）**，不会拿矿雷画面去匹配花朵帧。
   已复查：**之前产出的全部花朵 summary 都是显式带 `--style flower` 跑的**
   （`ANIMF_flo_a` / `ANIMF_flo_d0` / `d35` / `d70` / `d105` / `d140` / `x0` / `x15`），
   帧号有效，无需作废重跑。
   反过来，有几轮**爆炸**是在应用还处于花园样式时跑的（画面和模板对不上），
   这些 summary 已**删除**：`ANIMF_exp_a`、`ANIMF_exp_v0`、`v25`、`v50`、`v200`、`v250`、`v300`。
2. **一帧都没截到时退出码非 0**：现在退出码 **3**，
   summary 里明确写 `"captured": 0` 和 `"frame_ids": []`，截到了则写 `"captured": N`
   并列出帧号 —— 可以直接当 CI 用。
