## 0. 一句话结论

**引擎层与 SPEC.md 写下的 Win7 规则逐条一致，本轮没有发现需要改引擎的不一致项**；

### 写这批测试时踩到的坑（记下来免得下次再踩）

第一次跑新用例时出现 **4 条失败**，逐条查下来**全部是我自己测试预期算错了，引擎行为是对的**：

```
FAIL 和弦：旗数吻合但旗插在安全格上、周围没有雷时，局面继续（不判负）
       false !== true
FAIL 计时契约：终局（胜/负）之后状态不再变化
       1 !== 3
FAIL 胜利：差一格没翻开就不算赢
       2 !== 1
FAIL 胜利：插旗插到超过雷数也不影响判定（计数器为负但局面能赢）
       3 !== 2
```

错在哪：

1. 「旗数吻合但周围没有未标雷」这种局面**不存在** —— 旗数 == 数字意味着旗数等于周围的雷数，
   只要有一面旗插在安全格上，就必然有雷没被标上，一和弦就引爆。预期本身是错的。
2. `scenario(2, 2, [3])` 里索引 3 是 (1,1)，我却去 reveal(0,0)（安全格），自然判不了负。
3. 2×2 盘里 `[3]` 是雷，(1,1) 是雷不是待开的格子，「差一格」该差的是非雷格。
4. 同上，reveal 了雷格，局面是判负不是判胜。

改法：把场景摆对（用 `scenario(rows, cols, mineIdx)` 直接指定雷的位置），
并且把「插错旗 → 翻不齐 → 赢不了」写成用例（这本身就是一条 Win7 行为，值得钉住）。

### 引擎层已知瑕疵（不是 Win7 行为差异，本轮没动）

`lose()` 把未插旗的雷 `cell.revealed = true`，但**没有**同步 `revealedCount`，
于是判负后「已翻开格数」与实际翻开格数对不上。Win7 没有这个内部计数器，不构成行为差异；
改动它还会牵动 UI 里 `revealedCount > before` 的动画判定，风险大于收益，故只记录不动。
