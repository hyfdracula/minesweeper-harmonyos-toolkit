## 0. 一句话结论

| 对话框 | 尺度 | 是不是整数倍 | 客户区一致率 | 整框一致率 |
|---|---|---|---|---|
| 游戏失败框（loss.jpg） | **k = 2** | **是**（966 = 483x2，576 = 288x2） | **92.50%** | 81.36% |
| 关于扫雷框（about.jpg） | **k = 2** | **是**（628 = 314x2，394 = 197x2） | **86.27%** | 68.28% |

**「像素级」这件事是成立的**：两个框在真机上的缩放都是**整数 2 倍**，每个参考像素正好占

（4 处，可修），一类是**参考图与实现本来就不同**（字体光栅化、Aero 玻璃、系统阴影、运行期数据、
有意改动的文案）。

## 1. 工具：`tools/pixel_diff.py`

用法一句话：

```
python tools/pixel_diff.py --ref 参考图 --shot 设备截图 --rect X,Y,W,H [--ref-rect X,Y,W,H]
                          [--scale K | --auto-scale] [--out 差异图.png] [--top N] [--json 结果.json]
```

- `--rect`：**`--ref-rect` 选中的那块参考图**在截图里的位置与尺寸（设备像素）；
  不给 `--ref-rect` 时它就是参考图整幅。
- `--ref-rect`：参考图里参与比对的区域（缺省=整幅）。
- `--scale`：整数放大倍数；不给就**按区域尺寸反推**并判断是不是整数倍；
  `--rect` 也不给时进入 `--auto-scale`：**暴力试 k=1..8 + 滑窗 SAD**自动定位
  （粗搜用最近邻缩小 8 倍，原分辨率再精修 top-3 个候选 k，按原分辨率 SAD 定胜负）。
- 重采样**一律最近邻**（我们的实现就是整数倍 + `imageSmoothingEnabled=false`，
  用双线性会把抗锯齿算成差异）。
- 输出：差异像素数/占比、逐通道 R/G/B 平均绝对差、最大单像素通道差、
  **差异最大的 N 个区域**（连通块，按**累计差异**排序，带截图坐标）、三联差异图
  （参考图 | 截图 | 差异热力图）、一行总结：
  `一致率 xx.xx% | 尺度 k=2（整数）| 最大单像素通道差 nn`。

独立运行：`python tools\pixel_diff.py --help` √

## 2. 怎么采的、怎么定位的（都不靠目测）

**采集**
- 失败框：开局后逐格点击直到踩雷（uitest 单点点击，65 次点击触发爆炸），抓屏
  `docs/verify/P90_lose_dialog.jpeg`。

  抓屏 `docs/verify/P90_about_dialog.jpeg`。

**定位（两种互相独立的方法，结果完全一致）**

| 方法 | 失败框 | 关于框 |
|---|---|---|
| A. 像素扫描找**最长连续暗线**（对话框外沿是一整圈孤立暗线，棋盘砖块的暗边只有几十像素长） | 顶边 y=1147（x 157..1122）、左边 x=157（y 1147..1722）、右边 x=1122 → 矩形 **x157..1122, y1147..1722** | 顶边 y=1238（x 326..956）、左边 x=326（y 1238..1632）→ 矩形 **x326..956, y1238..1632** |
| B. 工具 `--auto-scale`（模板匹配，暴力试 k=1..8） | k=2，位置 **(157,1147)** | — |

两者一致，说明定位可靠。

**尺度反推**：`--rect` 宽 / 参考图宽 = 966/483 = **2.000**，高 576/288 = **2.000**
→ 整数倍 √。关于框 628/314 = 2.000，394/197 = 2.000 √。

> 与实现的对应：`GameController.computeDialogScale()` = `max(1, min(2, density, (canvasW-32)/w, (canvasH-32)/h))`
> = min(2, 3.5, 2.58, 8.9) = **2**；`WinDialogPainter.draw()` 的几何乘 `sVp = dialogScale*pxScale`，
> 字号乘 `sDev = dialogScale`。所以参考像素 → 设备像素正好 ×2，没有半像素。

## 4. 差异逐条判定

### 4.1 【我们画错了】按钮边框线宽 —— 影响最大

`WinDialog.ets:545`

```ts
ctx.strokeStyle = b.borderColor ?? C_BTN_BORDER;
ctx.lineWidth = Math.max(1, sVp);        // <-- 问题在这
ctx.strokeRect(bx, by, bw, bh);
```

`sVp` 是「**一个参考像素**等于多少 vp」，这里 = `dialogScale * pxScale` = 2/3.5 = **0.5714 vp**。
`Math.max(1, sVp)` 把它抬成 **1 vp = 3.5 个设备像素** —— 非整数，Canvas 会**抗锯齿**，
而且 `strokeRect` 的线是**跨在路径两侧**的，一半画到了按钮外面。

实测（失败框第一个按钮的上边框，竖扫 x=250）：

| 参考像素 y | 原版 loss.jpg | 我们的截图 |
|---|---|---|
| 235 | (240,240,240) 客户区 | (148,148,148) |
| 236 | **(112,112,112) 平涂 1 行** | (110,110,110) |
| 236.5 | — | (148,148,148) |
| 237 | (252,252,252) 按钮面 | (240,240,240) |

即：原版的边框是**整整 1 个参考像素（放大后 2 个设备像素）的平涂 #707070，画在按钮内侧**；
我们是**上下共 4 个设备像素的明暗过渡（148→110→148）**，一半溢出到按钮外面。

**修法**（本任务只读不改，仅给建议）：
`ctx.lineWidth = sVp`（0.571 vp = 正好 2 个设备像素），并把边框画在矩形**内侧**：
`ctx.strokeRect(bx + sVp/2, by + sVp/2, bw - sVp, bh - sVp)`，或直接用 4 条 `fillRect` 画边框。

**顺带**：按钮**面**的渐变也不一样 —— 原版 252 -> 207 且底部有一行亮边 (243,243,243)，
我们 242 -> 209 没有亮边（`C_BTN_TOP='#f2f2f2'` / `C_BTN_BOTTOM='#d1d1d1'`）。

影响面：失败框按钮行 14767 个差异像素，占客户区差异的 **42%**。

### 4.2 【我们画错了】标题栏分隔线与客户区整体高了 1 个参考像素

这是**失败框客户区的第 1 大差异**（通宽的一行，2138 px，累计差异 323348）。

实测（竖扫 x=600，穿过标题栏底边）：

| 参考像素 y | 原版 loss.jpg | 我们的截图 |
|---|---|---|
| 28 | (196,193,220) 标题渐变底 | (76,72,95) / (67,64,81) **← 我们的分隔线在这里** |
| 29 | **(68,67,83) 分隔线** | (244,242,253) / (240,239,244) 已经是客户区 |
| 30 | (240,239,245) 客户区 | (240,240,238) |

原版的分隔线在 **ref y=29**，客户区从 **30** 开始；
我们的分隔线画在 **28**，客户区从 **29** 开始 —— **整体高了 1 个参考像素（2 个设备像素）**。

原因在 `WinDialog.ets`：
- 分隔线：`ctx.fillRect(oxVp, oyVp + (TITLE_H - 1) * sVp, w, 1 * sVp)` → 落在 ref 28；
  代码自己的注释写的却是「loss.jpg y=29」，说明本意就是 29，**少写了 1**。
- 客户区顶边：`cy = oyVp + TITLE_H * sVp` → 落在 ref 29，应当是 30。

改法：分隔线用 `TITLE_H`，客户区顶边用 `TITLE_H + 1`（同时 `ch` 少 1）。
注意：`WinDialog.ets:402` 的注释「客户区（loss.jpg x=8..474 / y=30..279）」本来就是对的，
是代码没跟上。

### 4.3 【我们画错了】关于框的雷图标用错了素材

`WinDialog.ets:323-324`：`icon: [0,0,25,25]`、`iconPos: [38,78,25,25]`

## 7. 注意事项

- 工具的 `--rect` 语义是「**`--ref-rect` 那块参考图**在截图里的位置」，
  不是「参考图整幅的位置」；参考图是整窗截图（about.jpg）而屏上只有对话框一块时，
  必须同时给 `--ref-rect` 和对应的 `--rect`。
- 比对一律**最近邻**：参考图是 96 dpi 原始像素，我们的实现是整数倍 + 最近邻画的；
  用双线性会把抗锯齿算成差异，比出来的数没有意义。
- 截图是 JPEG，参考图也是 JPEG，两者都有压缩噪声；
  阈值取「通道差 > 8」判为不同（工具默认 `--threshold 8`，范围限定 0..254）。
- 区域超出截图会被夹到图内并告警；参考图放大后的尺寸与 `--rect` 对不上时，
  工具只比重叠部分，并在总结行标注「[尺寸不符，仅重叠部分]」，此时的一致率不能当整体结论。
- 设备只用 `127.0.0.1:5557`；5555 是同事在用的，没碰。

| [P1] 连通块洪泛用 `p ± h` 找上下邻居，行跨度应为 `w`（非正方形比对区会连错块、可能越界） | **已修**：改为 `p ± w` |
| [P1] 尺寸不匹配时只统计重叠部分却仍报一致率 | **已修**：告警 + 总结行标注「[尺寸不符，仅重叠部分]」+ JSON 里加 `size_mismatch` |
| [P2] 越界裁剪仍用 `crop`（Pillow 补黑） | **已修**：新增 `crop_clamped()`，夹到图内并告警 |
| [P2] `--auto-scale` 搜的是整幅参考图而不是 `--ref-rect` 选中的那块 | **已修**：改为搜索选中的那块 |
| [P2] 粗搜没检查候选在原分辨率下放不下，`best2` 可能为 None 而崩 | **已修**：先查放得下，再对 top-3 候选做原分辨率精修并按原分辨率 SAD 定胜负 |
| [P2] 粗搜用 BILINEAR 缩小，违背最近邻约定 | **已修**：粗搜也改最近邻，并加原分辨率精修兜底 |
| [P2] top-N 按面积排序，不是按差异大小 | **已修**：按**累计差异**排序，输出里同时给面积与累计差异 |
| [P2] `--threshold` 不校验（255 会让任何两张图都 100% 一致） | **已修**：限制 0..254，越界直接报错 |
| [P2] 文件头示例与代码语义不一致 | **已修**：示例改成与代码一致 |

复审前后「一致率」这个主指标**没有变化**（一致率由掩码直方图算出，不依赖连通块统计），
变的是「差异最大的 N 个区域」的列表：修正后由「面积排序」改为「累计差异排序」，
失败框客户区的第 1 大差异因此从「按钮边框」变成「客户区上边线」（见 4.2），
并由此发现了第 4.2 条那个「分隔线高 1 个参考像素」的问题。
