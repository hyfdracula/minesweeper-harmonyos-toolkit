### 必须知道的 API 26 坑（全部实测过，别再踩）

1. **Canvas 坐标单位是 vp**；`PixelMap` 的 `srcRect` 在 API 18+ 也是 vp → 要乘 `pxScale`。
2. `onReady` 的类型声明在撒谎 → 用 `this.drawCtx = this.context`。
3. `ctx.font` 写 `"px"` 指的是**设备像素** → 字号用 `sDev`，几何用 `sVp = sDev * pxScale`。
4. **手势 API 没导出** → 用裸 `onTouch` 自己做（pinch/pan/长按）。
5. **`HitTestMode.Block` 在 API 26 上会把子节点的 `onClick` 一起打死** → 别用；用 `controller.inputLocked`。
6. ArkTS 严格模式：不能用 any/unknown、**静态方法里不能用 `this`**、不能重复标识符、
   不能用访问修饰符；`CanvasRenderingContext2D` 是**全局类型**（不用 import）。
7. 图集约定：`Theme.ets` 里的源矩形是**半尺寸逻辑坐标**（SPRITE_SCALE=2，TILE=18）；
   `draw()` 会把源矩形乘 `SPRITE_SCALE × pxScale`。1:1 的图（如 helpBoard.png 256×192）走 `drawWhole()`。

## 11. MiniMax 5 小时额度窗口与自动唤醒（2026-11-03 新增）

本会话用的模型是 MiniMax M3.1 Flash，走 MiniMax **M Plan**（coding plan）的 key
（`~/.dsh/.credentials.yaml` 里的 `MINIMAX_API_KEY`，base URL `https://api.minimaxi.com/v1`）。
它有一个 **5 小时滚动额度窗口**，经常不够用，所以要按窗口刷新点自动唤醒继续干活。

### 11.1 窗口规则（官方 usage-rules，已核对原文）

| | 5 小时窗口 | 周窗口 |
|---|---|---|
| 适用 | 文本 / 图像 / 音频等非视频模型 | 全部模型 |
| 起点 | **首次使用**那一刻 | 首次使用那一刻 |
| 时长 | 5 小时 | 7 天 |
| 结束 | 额度全部恢复，**下一次使用开启新窗口** | 同左 |

要点：**窗口结束时刻与窗口内用了多少无关** —— 官方原文的例子是「10:00 首次使用，
这个 5 小时窗口在 15:00 结束；即使额度在 12:00 就用满了，它仍然在 15:00 才重置」。
两个窗口**独立**重置，5 小时重置不会顺带重置周额度。

出处：<https://platform.minimax.io/docs/m-plan/usage-rules>

### 11.2 为什么必须自己算

API **不暴露**窗口信息：响应头里没有额度字段，body 里也没有；
`/v1/usage`、`/v1/quota`、`/v1/coding_plan/usage` 等端点全是 404。
所以只能从**本机会话日志的调用时间戳**反推。

### 11.3 工具：`C:\Users\19161\.dsh\mm_quota_window.py`


1. 扫 `~/.dsh/sessions/**/*.session.v4.jsonl.zstd`（用 `zstandard` 模块解），

**三个要点**（都跟直觉不一样，照原版来）：

1. 判据是「**棋盘已结束**」，不是「点到了某一格」——
   所以点棋盘上的**任何地方**都能跳：点格子、点格子旁边的空白、点状态条那一带，

**实现**（应用仓 `C:\Users\19161\saolei`，提交 `ca5548c`）：

- `GameController.skipGameOverAnimation()`：停掉 `Anim.stopTrip()` / `Anim.stopWin()`、
  撤掉爆炸音尾巴（`stopBombTail()` / `stopBombRunLoop()`），

  **先建框**（`buildDialog`）→ **再重画**（`draw`）→ **最后通知**（`onGameOver`）。
  函数最后打一条 `[Anim] 点击跳过结算动画（胜利/失败）`。
- 三条点击路径都堵：
  - `tap()` **开头**（在开格之前判 —— 判负的那一下点击本身不能把刚起的动画秒跳掉）；

## 14. 2026-11-04/05：音效修复（归属改正 + 音画对齐）

用户 2026-11-04 报了两条：

> 1. 音画不同步
> 2. 在点击第一个方块打开的时候，还是会播放一次开始音频，原版是只有方块波浪形展开的时候才播放一次

### 14.1 第 2 条的根因：`else if` 链把首点的规则吃掉了

原来的写法：

```ts
if (wasReady)            SoundPlayer.play(Sound.FIRST_PAINT);   // 首点：只响这一声
else if (adjacent === 0) SoundPlayer.play(Sound.ZERO_DEVELOP);
else if (opened > 1)     SoundPlayer.play(Sound.TILE_MULTIPLE);
else                     SoundPlayer.play(Sound.TILE_SINGLE);
```

`wasReady` 排在最前 → **首点永远只响 `firstPaint`**，
`zeroDevelop` / `tileSingle` / `tileMultiple` 在首点时一声不响。
用户听到的「又播了一次开始音」就是它。

两份复刻都不把音挂在首点上：

- **Qt 复刻** `linux-minesweeper-main/src/ui/MainWindow.cpp:41-48`
  （注释原文 *"The original's SingleReveal / MultiReveal pair."*）：
  判据是**翻开几格**（`order.size() > 1` → multiReveal，`== 1` → singleReveal）；
- **Lmy 复刻** `Minesweeper-master/Minesweeper/utf8/Minesweeper.cpp:1774-1797`：
  `zeroDevelop()` 是独立函数，判据是**被点那格的相邻雷数**，同样不看是不是首点。

而 `firstPaint` 是**发牌动画的配乐**：
**Lmy 复刻** `Minesweeper.rc:344`（`IDR_WAVE1 = firstPaint.wav`）+
`utf8/Minesweeper.cpp:1495-1508`（在发牌的逐格绘制循环**之前** `PlaySound(IDR_WAVE1)`，
每格延时 `1100.0/(row*col)` → 总共 1100 ms）。

**已改**：首点删掉 `wasReady` 分支，按翻开格数走；发牌改播 `FIRST_PAINT`。
`Sound.GAME_START` 现在**全仓无调用点** —— 两份复刻对「发牌那一刻响哪一条」互相矛盾
（Qt 说 gameStart，Lmy 说 firstPaint），**要定案得在真 Win7 上试听一次**，
在此之前不擅自补播（免得多出一声）。详见 `docs\SOUND-MAP.md`「两份复刻与分歧」。

### 14.2 第 1 条的根因：两套时钟

画面走 `Date.now()` 的**绝对时间轴**（`dealStart` / `rippleStart` / `Anim.tripElapsed`），
声音却从「调用 `play()` 的那一刻」开始**异步**准备播放器
（`getRawFd` → `createAVPlayer` → 等 `initialized` → `prepare` → `seek` → `play`）——
几百毫秒全花在**该响的那一刻之后**。

**已改**（`SoundPlayer.ets`）：

1. `warmup()`：启动后提前把播放器建好并 `prepare`（挂在 `MinefieldCanvas.ets` 的
   `setTimeout(..., 0)` 上，让首帧先画完）；
2. `playAt(name, atMs)`：把「该响的绝对时刻」交给声音层，按剩余时间补偿；
   发牌配乐、翻开声、爆炸三段、胜利音都改用它；
3. 重播分两档：`playing` 时直接 `seek(0)`（`play()` 只在
   `prepared`/`paused`/`completed` 可调，在 `playing` 下调用会抛 5400102），
   其余状态才走 `stop → prepare → seek → play`。

### 14.3 顺带修的三处

| 问题 | 依据 | 改法 |
|---|---|---|
| 爆炸中音比画面**早 425ms** | 切换点抄了参考实现的 575ms（25 帧 × 23ms），但本工程爆炸是 23 帧 × 43.478ms = **1000ms** | 用 `Anim.explodeDurationMs()`；三段都锚到级联的绝对起始时刻 |
| `tap()` 里的 `invalidMove` 分支是**死代码** | `reveal()` 返回 `changed=false` 只有两种可能（终局 / 已翻开或已插旗），而那分支要求的是**相反**条件 | 删掉。依据：Qt 复刻 `BoardWidget.cpp:833-849`，`emit invalidMove()` 只在**和弦失败**时出现 |
| `gameLose` 只播一次 | 原版是**每颗雷各炸一声、可叠加**（Qt 复刻 `Sounds.h:10-12`：原版留 30 个缓冲），而且**由动画时钟触发**（`BoardWidget.cpp:305-306` 环走到这颗雷时才 emit）—— 那就是原版的音画同步机制 | 按每颗雷的 `boom.startMs` 逐颗触发 + 4 个播放器轮转的池子 |

### 14.4 怎么自动验证「这一声到底响没响」

音效是**听觉**的，像素断言抓不到。但应用每播一声都打一行日志：

```
[Sound] 播放 <名字> at=<时刻>            —— 立即播放
[Sound] 对齐播放 <名字> at=<时刻>         —— 对齐到画面的绝对时刻
```

于是「这一刻播了哪一声」可以用日志断言 —— 硬且可复现。

**新增** `tools/click_cases/sound.json`（8 条用例）与跑测器的新断言类型 `hilog_checks`
（在**同一个日志窗口**里做多条检查）。

**为什么不能用两个 `hilog_regex`/`hilog_absent` 连着写**：
`log_new_lines()` 每读一次就把读到的行标成「已见过」，
所以连续两个 expect 看不到同一批日志 —— 第二个会**空跑通过**（假的绿灯）。
实测踩到过：首轮「首点只播一声」那条用例**假通过**，
因为它数到了两条重复日志（`playAt` 调度时一行 + `play()` 实际播放时一行）。

### 14.5 亮屏守护脚本（新增，不用 token）

`tools\keep_awake.ps1`（纯 PowerShell，只调 hdc）+ `tools\keep_awake.cmd`（双击版）。
原理：`power-shell timeout -o 7200000` 把息屏倒计时设成 2 小时，
但它是**一次性的**，所以脚本每隔几分钟重新拉满。

**三个坑**（都踩过）：

1. **`-o` 的单位是毫秒** —— 写 7200 是 7.2 秒（看着像设了 2 小时，其实几秒就黑屏）；
2. **PowerShell 5.1 把无 BOM 的 UTF-8 当 GBK 读** → 中文乱码把字符串括号弄坏，
   直接语法报错。脚本已加 **UTF-8 BOM**；
3. **`param get` 在这台设备读不回持久化参数**（errNum 1002），
   所以脚本不靠它，改用 `hidumper` 读回 `OverrideTimeout` **自检**。

### 14.8 顺带修掉的**跑测器老 bug**：平板上认不出棋盘网格

**症状**：真平板上，凡是「要先造出判负/判胜局面」的用例
（`board.restart.after_gameover`、`sound.lose.*`、`sound.win`）
要么卡 40 轮轮询后报「应用启动后仍找不到棋盘网格（已重拉 3 遍）」，
要么一条都跑不完（每轮一次截图 ≈ 2.5 秒，40 轮 = 100 秒 × 3 遍 = 5 分钟）。

**根因**（`tools\win_probe.py` 的 `find_grid_by_seams`）：
`candidates()` 的阈值原来是 **全图最大值 × 0.55**。

而屏幕顶部那条**系统状态栏是整行全黑**的：
在真平板横屏（2800×1840）实测，它的行计数 = **2800**（整屏宽），
于是阈值 = 2800 × 0.55 = **1540**；
而真正的**横缝**（棋盘宽 ≈ 1296）**全被砍掉** → 一个横缝候选都找不到。

列方向没事，是因为列剖面的全图最大值（1452）恰好来自竖缝本身。
**所以这是「按极值定阈值」的通病，跟具体机型有关** ——
横屏、状态栏更宽的机器上才会暴露。

**修法**（两处）：

1. 阈值改成**跟 pitch 挂钩**：`thr = max(20, 2 * pitch)`。
   一条缝的暗像素支撑 ≈ 棋盘在另一个方向上的边长，至少也有 3 格，
   所以 2 格宽当门槛绰绰有余，**且不受「整行全黑」这种极值污染**。
2. `validate_grid()` 不再只取「最长那条链」，而是**逐条候选链**
   用版式（hilog 里的棋盘原点）去挑吻合的那一条 ——
   因为最长那条可能是「状态栏 + 前 9 条横缝」拼出来的**假链**
   （行数多一个、起点偏 138 px）。
   实测修好后：`validate_grid` 返回 `(753, 181, 9x9)`，
   `dx=1 / dy=88` 都落在允许范围内，`detect_theme` 认出 `blue` ✓。

**这个 bug 跟本轮的音效改动无关**（旧图 `CM_1335tabfull2_board_first_click.jpeg`
跑同一个函数也是 None），但它让平板上**所有依赖造局面的用例**都跑不动，
不修就没法验证音效的判负/判胜部分。

### 14.11 音画同步现在是**可测量**的了

用户报的「音画不同步」原来只能断言「走了对齐播放那条路」——
量不到误差本身，而用户抱怨的就是误差。

2026-11-05 加了两样东西：
1. 应用在涟漪起点打 `[Anim] 涟漪开始 at=<ms> 格数=<n>`；
2. 跑测器 `hilog_checks` 支持 `delta`：取两条日志各自的时间戳相减，
   要求 `|差| <= abs_max`（这里定 60ms —— 人耳察觉阈值约 80~100ms，
   帧定时器 30ms 一格，留两格余量）。

**实测（模拟器）：音画差 = 0 ms**：
```
[Anim] 涟漪开始 at=1793849839992 格数=43
[Sound] 对齐播放 zeroDevelop at=1793849839992
```

**这个 0 的含义要说清楚**：它量的是**排期**差（声音是不是锚在同一时刻），
**不是**扬声器物理出声的延迟 —— 后者得录音才能量，纯软件测不出来。
改之前那几百毫秒的「现建播放器」延迟才是用户听到的不同步；
现在播放器预热过，剩下的只有 `play()` 的毫秒级启动时间。

## 15. 2026-11-06：两个动画混杂（发牌 vs 翻开涟漪）

用户原话：「两个动画混杂了，动画1是进入扫雷页面，未打开的各自从中间向两边打开的动画，
波纹状。动画2是点击未打开方块翻开的动画，我希望动画2能打断动画1」。

### 15.1 根因

`dealActive`（发牌波浪）和 `rippleActive`（翻开涟漪）是**两套独立的动画状态**，
`tickFrames()` 里同时推进（`tickDealIn()` + `tickRipple()`），
所以在发牌还没放完时点一格，画面上就是「一半格子还在波浪弹起、另一半已经在涟漪淡入」。

### 15.2 原版是**能打断**的（这点很关键：不是增强，是补齐保真）

依据 [Lmy] `Minesweeper.cpp:1843-1879` 的 `speed()`：

```c
//鼠标消息停止动画效果
if ((optionFlag & OF_DRAW) && (!PeekMessage(&msg, NULL, 0, 0, PM_REMOVE)
    || (msg.message != WM_LBUTTONDOWN && msg.message != WM_RBUTTONDOWN)))
{ ... Sleep(dwMilliseconds); ... }
else
{
    msgFlag = true;
    PlaySound(NULL, NULL, SND_ASYNC);   // ← 连声音一起停
}
```

- 判据是**消息类型**，不看坐标 ⇒ 鼠标在窗口**任何位置**按下都算；
- 左键**和**右键都算；
- 命中后 `msgFlag = true` ⇒ 后续 `speed()` 不再 `Sleep` ⇒ 剩下的格子**瞬间全部画完**（不是冻结在半截）；
- 并且 `PlaySound(NULL,...)` 把正在播的配乐也停掉。

参考实现那段发牌循环上方还留着原作者的注释
`//bug	WM_LBUTTONDOWN停止动画, WM_LBUTTONUP消息会初始化mapInfo` ——
它把这当成自己的 bug，但那是原版的真实表现。

**顺带纠正一处文档错误**：应用仓 `README.md` §5 原来写「开局发牌动画不能点击跳过」，
那是错的，原版能打断。已改。

### 15.3 实现

1. `GameController.interruptDealIn()`：`dealActive = false` → `dealFlags = []`
   （清空的直接效果就是每格都算「已弹起」= **瞬间画完**）→ `SoundPlayer.stop(FIRST_PAINT)`
   → 打一行 `[DealIn] 发牌动画被打断 elapsed=<ms>`（给跑测器断言用）。
2. `MinefieldCanvas.handleTouch()` 在最前面（`inputLocked` 判断之前、
   `touches.length>=2` 判断之前）对 `TouchType.Down` 调它 ——
   这样「按哪都断、几根手指都断、拖动也断」，与原版「任何按下消息」一致。
   放在 `tap()`（抬手）里是不对的：按下到抬手之间动画还在跑，而且拖动/捏合根本不走 `tap()`。

### 15.4 顺带修掉的第二个问题（Codex 复审抓到的 P2）

`SoundPlayer.stop(name)` 原来只撤「还没到点的定时器」+ 停当前播放器，
**挡不住已经进了 `prepare()` 的播放请求** —— 于是「按下打断发牌动画之后，配乐才响起来」。
`playAt()` 给的时间通常已经到点，请求会立刻进入异步链、根本不在定时器里。

修法：给普通音效也加**取消代次**（同池子那套）：`stop(name)` 把代次 +1，
`playAsync()` 取调用时刻的代次并把它当取消判据传进 `playOn()`，
`playOn()` 在真正 `play()` 之前查一次。
