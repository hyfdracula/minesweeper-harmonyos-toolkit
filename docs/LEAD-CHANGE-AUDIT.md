## 1. 问题清单（按严重度）

### L1 [HIGH] 「抬一档」把「本来完全装得下」的盘面变成大幅溢出，且初始视图顶部藏在菜单栏后面（看不见也点不着）

- **改的哪一处**：`GameController.ets:270-272`（抬一档规则）+ `307-308`（纵向居中）
- **问题**：抬档规则只看「格子太小」，不看「抬完会不会反而装不下」；而纵向用**居中**而不是顶对齐，溢出被劈成两半，**上面那一半永远压在菜单栏下面**。
- **推演（外屏 1323×1000，菜单栏 72px）**：
  - 高级 30列×16行，n=1：`bw=30×18×2=1080 ≤ 1323` ✓，`bh=16×18×2+32×2=640`，`72+640=712 ≤ 1000` ✓ → **本来完全装得下**。
  - 抬一档 → n=2（tile=72）：`frameW=30×72=2160`（横超 **837px**），`frameH=16×72+32×4=1280`（纵超 **352px**）。
  - 初始 `panY=0` → `frameY = 72 + round((1000-72-1280)/2) = 72 - 176 = **-104**` → 棋盘顶边在画布上方 104px，菜单栏（0..72）压住 **176px** 的棋盘。
  - 可见量：`1323/72 = 18.4/30 列`、`(1000-72)/72 = 12.9/16 行`。
  - 菜单栏区（y 0..72）的点击被 `isOnMenuBar()` 判给菜单 → **顶部约 2.4 行棋格既看不见也点不着**，必须先平移（`limY=176` → 顶边可平移到 y=72 ✓ 能到，但要用户自己发现）。
  - 中级 16×16 同样：n=1 完全装得下（648×776）→ 抬到 n=2 → `frameH=1280 > 928` → 纵超 352px、初始 `frameY=-104`。
  - 内屏 2210×1616，自定义最大 30列×24行：fit=1 → 抬到 2 → `frameH=1856 > 1544` → `frameY = 72-156 = -84`，156px 藏在菜单栏下。
- **期望**：① 抬档只在**横向**装不下时才有收益（格子变大是为了点得准），纵向装不下时抬档只会更糟；② 内容高于视口时应当**顶对齐**（`frameY = menuBarPx`），把溢出全放到下面（滚动语义），而不是居中。
- **实际**：横向、纵向一起抬；纵向用居中 → 溢出的上半截永久藏在菜单栏后。
- **建议**：
  1. 抬档前先算新档位的 `bw`：只有 `bw > canvasW`（横向真的超了）才值得抬；纯纵向装不下时保持原档位。
  2. `frameH > availH` 时改成顶对齐：`frameY = menuBarPx + panY`，同时 `limY` 从 `(frameH-availH)/2` 改成 `(frameH-availH)` 并把 pan 的语义改成「只向一个方向拖」。
  3. 棋盘溢出时给一个「可拖动」提示（当前完全没有）。

### L2 [MEDIUM] `limX/limY` 与 `frameX/frameY` 不同源 → 边缘可达性有 ≤0.5 设备像素误差

- **改的哪一处**：`GameController.ets:306-308`（`Math.round`）vs `330-331`（`lim` 用未取整半差）
- **推演**：`base = Math.round((1323-2160)/2) = Math.round(-418.5) = **-418**`（JS `Math.round` 向 +∞ 取整）；
  `limX = (2160-1323)/2 = **418.5**`。
  - `panX=+418.5` → `frameX = 0.5` → 左边缘差 0.5px 到不了 0
  - `panX=-418.5` → `frameX = -836.5` → 右边缘 = `1323.5` → 差 0.5px 到不了 1323
  - **结论：左右都能拖到**（各差 0.5 设备像素 = 0.18vp），最后一列最右 0.5px 出屏。
- **期望**：`lim` 应由**取整后**的 base 推导，两边严格对齐。
- **建议**：`clampPan` 里让 base 与 lim 共用一个量，例如先算 `const baseX = Math.round((this.canvasW - this.frameW)/2)`，`limX = this.frameW > this.canvasW ? -baseX : 0`；纵向同理（base 要含 `menuBarPx`）。

### L3 [MEDIUM] `v()` 的取整达不到注释宣称的目的（对话框内部仍是小数坐标），还引入「画与点」两套取整

- **改的哪一处**：`GameController.ets:232-234`（注释说「对话框的缩放是小数，按钮、文字全在半像素上」）
- **推演**：外屏 1323 画布，统计窗口 `scale = (1323-32)/702 = **1.8390**`（小数）。
  标题栏下沿 29 参考像素 → `29 × 1.8390 = **53.3 设备像素**` → 仍落在分数像素上 → **抗锯齿照旧**。
  `v()` 的取整只把**窗口位置**挪到整数像素，窗口**内部**的边（按钮、列表框、文本）依然是小数坐标。
- **期望**：要锐利，应在「参考像素 → 设备像素」这一级取整（`scale` 取整到 0.5/1 的倍数，或 painter 每步取整）。
- **建议**：`computeDialogScale` 返回 `Math.round(s*2)/2` 之类的半整数，或让 painters 用设备像素整点画；`v()` 的取整对棋盘的地板/凹槽线确实有效，可以保留，但**注释要改**，别让人以为问题已经解决。

### L4 [MEDIUM] `computeDialogScale` 的 `Math.max(1, …)` 在小画布上让窗口比屏幕大、按钮跑到屏外

## 2. 一句话总结

**这一轮最可能出事的一条是 L1**：`layout()` 的「抬一档」规则（`GameController.ets:270-272`）不看横向是否真的超宽就抬，加上 `applyGeometry()` 纵向用**居中**而不是顶对齐（307-308），结果在外屏 1323×1000 上把**本来完全装得下的高级局**（30列×16行，n=1 时 1080×640 稳稳放下）变成 `frameW=2160 / frameH=1280` 的溢出盘，初始 `frameY=-104`，**棋盘顶部 176px 被菜单栏压住（`isOnMenuBar` 吃掉那片点击），用户第一眼看到的是一盘缺了顶部的棋盘**，而界面上没有任何「可以拖动」的提示；能拖是能拖（`limX=418.5`，左右各差 0.5px，见 L2），但初始视图先输了。
