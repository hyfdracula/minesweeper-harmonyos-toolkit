## 1. 音效全哑（AVPlayer 的 fdSrc 是异步状态机）

**问题**：菜单里「声音」是勾着的、rawfile 里 11 个 wav 都在，但**一个音效都不响**。

**根因**：`p.fdSrc = { fd, offset, length }` 不是同步赋值，它是一次 **idle → initialized 的异步状态切换**。
旧代码设完 `fdSrc` 立刻 `await p.prepare()`，抢在状态切换完成之前，抛
`The current state is idle. Prepare operation only supports stopped/initialized`，于是**每一个**音效都在
`prepare` 这一步就失败了。

**修法**：注册 `stateChange` 监听 → 赋 `fdSrc` → **等 `stateChange` 回调收到 `initialized` / `prepared` / `playing`**
再 `prepare()`；另加 3 秒超时保护（超时抛「等待 initialized 超时」），`state === 'error'` 时直接 reject。

**证据**：

- 代码：``SoundPlayer.ensurePlayer()``（`ensurePlayer`），其中错误原文在 ``SoundPlayer.play()``，
  监听在 ``SoundPlayer.ensurePlayer()` 的 `stateChange` 回调`，`prepare()` 在 ``SoundPlayer.ensurePlayer()` 的 `stateChange` 回调`。
- 修复位置：commit `8925f0e`。
- 旧版症状与修法记录在 ``SoundPlayer.play()`` 的注释里（真机踩到，不是推测）。

**未验证**：本条只到「代码改对」为止。**音效是否真的出声、在真机/模拟器上听感如何，本轮没有实测记录。**

## 2. 对话框按钮点不动（输入锁把点击一起吞了）

**问题**：结束对话框、统计窗口、自定义难度框上的按钮，点了**完全没反应**。

**根因**：`inputLocked` 改成派生属性之后，`MinefieldCanvas.handleTouch` 一进来就 `return`：

```ts
if (this.controller.inputLocked) { return; }   // 旧写法
```

`inputLocked` 的语义是「**有对话框开着，别让棋盘乱动**」，但旧写法把它当成了「**整个画布都不响应触摸**」。
对话框的按钮也是画在这块画布上的，于是按钮的点击被同一个锁挡掉了。

**修法**：改成「**锁定只禁平移与捏合，点击照常通过**」——
``MinefieldCanvas.handleTouch()`` 里 `inputLocked` 为真时只拦 `Move`/`双指` 路径，`Down`/`Up` 继续往下走，
让菜单、对话框、统计窗口、自定义框各自去处理。

**证据**：

- 代码：``MinefieldCanvas.handleTouch()`` 的注释「有对话框 / 统计窗口 / 自定义框开着时：**只让点击通过**，不做平移与捏合。」
- ``GameController.inputLocked`` 的 `inputLocked` 派生属性定义。
- 修复位置：commit `8925f0e`。
- `CUSTOM-DIALOG-AUDIT.md` §0 问题三的核实结论也指向同一处：「模态锁也没有吃掉按钮点击
  （``MinefieldCanvas.handleTouch()`` 只放行 Down/Up 而不是直接 return）」。

## 4. 自定义局重开变成初级盘

**问题**：开一个 20×20×50 的自定义局，点菜单「新建(F2)」或结束框「再玩一局(P)」，
盘面变成 **9×9 初级盘**。

**根因**：`restart()` 用的是 `configOf(this.difficulty)` —— 按**难度预设**取行列与雷数，
而不是**当前盘面**的参数。自定义局不改变 `this.difficulty`，于是它被当成上一次选的那个难度重开。

**修法**：``GameController.restart()`` 改成直接取引擎当前的行列与雷数：

```ts
const rows = this.engine.rowCount;
const cols = this.engine.colCount;
const mines = this.engine.mineCount;
```

`customGame` 标记**保留**（重开后的这一局仍是自定义局，仍不进统计 —— Win7 的规则就是自定义局不计入获胜率）。
只有引擎还没开过局（行列为 0）时才回退到难度预设。

**证据**：

- 代码：``GameController.restart()``（含坑的完整注释），标记位 ``GameController.openCustom()``。
- 修复位置：commit `8925f0e`。
- 原始发现：`CUSTOM-DIALOG-AUDIT.md` 的 **P1 [HIGH]**「自定义局的「新建 / 再玩一局」会把盘面换成难度预设」。
- 统计侧独立核实（`CUSTOM-DIALOG-AUDIT.md` §0 问题二）：`GameStats.record()` 是全工程唯一会动
  `played/won/currentStreak/maxStreak/bestSeconds` 的地方，被 `if (!this.customGame)` 包住，**自定义局确实没进统计**。

## 5. 版式算错（本轮最大的一处改动）

### 5.1 缩放预算把看不见的玻璃边框算进去了

**问题**：`layout()` 里算「整盘刚好放下」的档位 `fit` 时，用的是**原版窗口底板 frame** 的尺寸，
也就是「棋盘 + 四周 59×62 个参考单位的玻璃边框留白」。可手机版**根本不画那个边框**
（`drawBoardArea()` 只在棋盘矩形内填白地板加三边 1px 凹槽线）。
那 59/62 单位纯属白占缩放预算，把高级局在窄屏上压到 n=1（格边 36 设备像素 ≈ 10~13 vp，手指根本点不准）。

**修法**（``GameController.layout()``）：预算只按**真正画出来的东西**算：

```
横向预算：棋盘宽 = 列数 × 18 × 2n
纵向预算：菜单栏高 + 棋盘高 + 状态条带(32×2n)
```

配套：**棋盘 + 状态条这一组在菜单栏以下的区域居中**（菜单栏进竖向预算），
见 ``GameController.applyGeometry()``（`frameY = menuBarPx() + round((canvasH - menuBarPx() - frameH)/2) + panY`）。

**证据**：`LAYOUT-MATRIX.md` v2.0 §7 的旧新对照表，**7 个组合各升一档**：

| 画布 | 难度 | 旧 n（格边 px） | 新 n（格边 px） |
|---|---|---|---|
| Pura X Max 内屏 | 初级 | 3（108） | **4（144）** |
| Pura X Max 外屏 | 初级 | 2（72） | **4（144）** |
| Pura X Max 外屏 | 中级 | 1（36） | **2（72）** |
| Mate X7 | 初级 | 4（144） | **5（180）** |
| Mate X7 | 高级 | 1（36） | **2（72）** |
| Mate 90 Pro | 初级 | 2（72） | **3（108）** |
| Mate 90 Pro | 中级 | 1（36） | **2（72）** |

### 5.2 `clampPan` 在放得下时也允许拖偏

**问题**：平移夹紧用 `|(画布 - 底板)/2|`，即使整盘放得下，初级局也能被拖偏几百像素。

**修法**：``GameController.clampPan()`` 的 `clampPan()` 改成按「棋盘比视口大多少」夹，
放得下时平移量归零；比视口大时才允许拖，两边都能拖到。

**证据**：`LAYOUT-MATRIX.md` v1.0 的 **P2-6**（v2.0 编号下并入 §4 的取舍类）；
`SPEC.md` §11.8 第 1 条记录了同类问题的上一轮修法（commit `c32e2e6`）。

### 5.3 装得下但格边 < 48px 时抬高一档（新增规则）

**问题**：`LAYOUT-MATRIX.md` v2.0 判定为 **P0-1**：30 列的局在窄屏上宽度是**几何必然**装不下，
装得下的那一档只有 n=1（格边 36 设备像素 ≈ 10~13 vp），手指点不准。

**修法**（``GameController.layout()``）：装得下的那一档如果格边小于**最小可点格边 48 设备像素**，
就往上抬**一档**，让棋盘横向超出画布，靠平移看（`clampPan` 本来就支持）。

```ts
if (TILE * 2 * fit < MIN_CELL_PX && fit < MAX_SCALE_INDEX) {
  fit = fit + 1;
}
```

常量 `MIN_CELL_PX = 48` 定义在 ``Theme.MIN_CELL_PX``。

**依据**：用户原话「外屏不接受降级，我希望可以拖动放大」——
**宁可超宽也要能点准**，而不是给一个点不中的棋盘。

**证据**：``GameController.layout()`` 的注释、``Theme.MIN_CELL_PX`` 的常量说明。

> **重要提醒**：`LAYOUT-MATRIX.md` v2.0 的数据表是 **13:35** 写的，
> 而 `MIN_CELL_PX` 抬一档规则是 **13:39** 才加进 `Theme.ets` 的。
> 所以 v2.0 表里「窄屏 + 高级 16×30 = n=1」那几行**已经过期**：
> 按当前代码，格边 36 < 48 会抬到 **n=2（格边 72）**。
> `LAYOUT-MATRIX.md` 是只读报告，本轮没有改它；**重跑 `tools\check_layout.py` 才能拿到与当前代码一致的数字**。

**复测（13:41 build，Mate 90 Pro）**：规则按预期生效 ——
高级 30 列从 n=1（格边 36）抬到 **n=2（格边 72）**，棋盘宽 1080 → 2160 px，

>
> **抬档只看「格子太小」，不看「抬完会不会反而装不下」**；而纵向用**居中**而不是顶对齐，

### 5.4 文字与边框落在分数设备像素上

**问题**：`v(px)` 原来直接 `px * pxScale`，于是**落在分数设备像素上**的矩形与文字会被抗锯齿糊掉
（对话框的缩放是小数，按钮、文字全在半像素上）。像素级复刻要求边缘锐利。

**修法**（``GameController.v()``）：先取整再换算。

```ts
private v(px: number): number {
  return Math.round(px) * this.pxScale;
}
```

**证据**：``GameController.v()``（含坑的注释，标注来源为 LAYOUT-MATRIX 审计 P2-6）；
`LAYOUT-MATRIX.md` v2.0 §1.1 表最后一行也记着 `v(px) = Math.round(px) * pxScale`。

### 5.5 对话框缩放统一（原来自定义框一直用陈旧初值 1）

**问题**：`computeDialogScale()` 只被结束对话框用；**自定义难度框一直用陈旧初值 1**。
`CLICK-MATRIX-X7.md` 的异常 A1 实测：自定义框在内屏上只有约 **260 × 190 设备像素（约 83 × 61 vp）**，
正文文字每汉字约 **8~9 设备像素高（约 2.7 vp）**，而同屏的菜单栏文字是 43.75 设备像素（14vp），
**两者差 5 倍**；数字键盘每个按键只有约 **32 × 32 设备像素（约 10 vp）**，手指点按容错极低。

**修法**：``GameController.computeDialogScale()`` 的 `computeDialogScale(refWidth, refHeight)` 统一三个对话框
（结束框、统计窗、自定义框）的缩放，公式按**物理密度**算 + 保证放得下 + **封顶 2 倍**：

```
s = max(1, min(2, density, (canvasW - 32) / refWidth))
```

调用点：``GameController.computeDialogScale()``（结束框）、`:1180`（统计窗）、`:1281`（自定义框，
注释明写「自己算缩放，别用 dialogLayout() 的陈旧值」）。

**证据**：`CLICK-MATRIX-X7.md` 异常 A1（实测尺寸与公式推导）；
`LAYOUT-MATRIX.md` v1.0 的 **P2-7**（v2.0 §7 列为「已修：computeDialogScale 统一缩放，自定义框不再用陈旧值」）。

**复测（13:41 build）—— 已通过**：

## 8a. Codex 对抗性复审（CONCERNS）与对话框高度封顶

**复审裁定**：**CONCERNS**。
来源 = **由 P2 严重级别标记推断**（模型没有给出显式的 VERDICT 行）。
只有一条问题：

**问题**：对话框缩放**只按宽度封顶**，短画布（横屏、分屏）上对话框会**超出屏幕高度**，
底部按钮跑到屏幕外点不到。
实测例：900×400 画布 @密度 2.75，396×340 的胜利框 ×2 = 792×680，按钮全在屏外。

**修法**（``GameController.computeDialogScale()``）：`computeDialogScale` 把**高度也纳入封顶**。

```ts
const density = 1 / this.pxScale;
const maxByWidth  = Math.max(1, (this.canvasW - 32) / refWidth);
const maxByHeight = Math.max(1, (this.canvasH - 32) / refHeight);
return Math.max(0.5, Math.min(2, density, maxByWidth, maxByHeight));
```

另外 `dialogLayout()`（``GameController.dialogLayout()``）在对话框比画布还高时改成**顶对齐**，
不再居中（居中会让上下各露一半，底部按钮够不着）—— 对应 `LEAD-CHANGE-AUDIT` 的 **L4**。

**修复位置**：commit `9a70112`。

### 9.2 `tools\probe_canvas.py` 新增，以及它自己踩的坑

原理：从 `x = 棋盘原点 + 格边/2` 那一列往下扫，第一段连续够长的「砖色」像素就是棋盘第一行的顶边；
棋盘顶边（屏幕）− 棋盘原点（画布）= 画布顶在屏幕上的偏移。

**坑**（`probe_canvas.py:15-17` 原文）：采样点原来取 `boardX+4`，正好落在砖块**左缘那道暗边**上
（RGB 31,56,97，b=97 不过阈值），于是扫到的是砖块中间才命中的位置，**偏移算成 225（实际 121）**，
后面的点击全偏。必须取**格边中心**。

代码现在取 `bx + tile // 2`（`probe_canvas.py:45`）。

**交叉验证**：`CLICK-MATRIX-X7.md` 异常 A2 独立量出画布顶在**屏幕 y ≈ 121**，
与脚本修正后的结果一致（同样是 121）；A2 当时还指出「任务里写的 109」与实测差 12 px。

### 12.1 状态条计数器改成**真七段数码管**

**问题**：状态条上的计时与剩余雷数用 `ctx.font = bold …px sans-serif` 画白字，
**不是原版的形制**。

**根因与证据**：2026-10-31 上午本文件曾写「计数器用粗体白字**不是降级**」，
理由是「参考实现 `linux-minesweeper/src/ui/BoardWidget.cpp:552-559` 就是
`setBold(true)` + `setPen(Qt::white)` + `drawText` 居中」。
**这个论证是错的** —— 参考实现怎么画只能说明**那一份复刻**怎么画，
不能证明**原版**长什么样。

**权威证据**：**微软原图 `win7-assets\images\helpBoard.png`** 的状态条里「18」「40」
**逐像素反推**，能读出七段的结构、负号是独立的一段、右对齐不补零。
完整几何表（逐段坐标、置信度、出处）在 **`docs\SEVEN-SEG-COUNTER.md`**。

**修法**：新增 `common\SevenSeg.ets`（Canvas 画段），接线在 `GameController.drawStatusStrip()`。

| 项 | 值 |
|---|---|
| 面板 / 槽位 | 40×21 参考像素，**3 槽**，槽距 **13** |
| 对齐 | **右对齐、不补零** |
| 负号 | 独立的一段（中段 g） |
| 显示区间 | [-99, 999]，超出钳到端点 |
| 亮段颜色 | `#FAFAFC` |
| 「1」的形状 | 带原版的**衬线小旗 + 衬线底横**：竖笔在格的**右边**（x 9..11），旗贴在竖笔左上角，底横以竖笔为中心**向两侧伸出**（x 7..11） |
| 「1」的段掩码 | `0x186` = b + c + 衬线旗（`SEG_FLAG`，**第 8 段**）+ 衬线底横（`SEG_BASE1`，**第 9 段**）。注意底横**不是**标准 d 段（标准 d 横跨格宽中间的 x 3..8），是单独画的一段 |

> **七段字形清晰可见**（上横 / 上下竖 / 中横 / 下横逐段分明），与旁边银色尖刺地雷图标同框。

> **顺带核实了纵向居中：没有偏差。**（此前曾怀疑「外屏没垂直居中」，那是误判，已作废。）
>
> `GameController.applyGeometry()` 的公式是
> `frameYBase = groupFits ? menuPx + round((availH - boardH - stripH) / 2) : menuPx`，
> 其中 `menuPx = GameController.menuBarPx()` = round(`MENU_BAR_H` / pxScale)，
> `MENU_BAR_H = 18 × (14/12) = 21 vp`（`WinMenu.MENU_BAR_H`）。

> | 机型 | 日志棋盘原点 | 公式算出来 | 吻合 |

> | Mate 90 Pro 初级 | (154, 754) | 74 + round((2524-972-192)/2) = **754** | 是 |
> | Mate X7 外屏 初级 | (54, 569) | 66 + round((2170-972-192)/2) = **569** | 是 |

> 与推算的 121（画布顶偏移）+ 569 = **690** 一致；菜单栏下沿 = 121 + 66 = 187；
> 状态条带 1662..1854；画布下沿 = 121 + 2236 = 2357
> → **上留白 503 px、下留白 503 px，精确相等**。
