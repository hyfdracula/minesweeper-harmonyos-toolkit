### 1.2 脚本口径

- `Math.round` 用 `floor(x+0.5)` 复刻（Python 内置 `round` 是银行家舍入）。
- 平移量取 `panX = panY = 0`（新局、未手动缩放）；`limX/limY` 另算并报出。
- 越界：矩形相对画布四边的余量出现负数。重叠：矩形相交面积 > 0。
- 整数像素：棋盘/底板/状态条四个元素的矩形、每一格的左上角、数字原点（`x+3u, y+1.5u`）。
- 状态条可见性：按元素的横向区间与 `[0, canvasW]` 求交，交集 > 0 记为可见（**部分可见也算可见，但会报出可见宽度**）。

1. **状态条改为锚画布左右沿**（`clockX = max(boardX + margin, margin)`、`iconX = min(boardRight - margin - 25u, canvasW - margin - 25u)`），不再跟棋盘宽度走 —— 与真 Win7 一致（原版雷数计数器贴窗口右边缘），且棋盘再宽也看得见；代价是状态条与棋盘左右不对齐（棋盘超宽时本来也不对齐）。**（主线程已实现，本文的脚本已同步）**
2. 或保留锚棋盘，但**棋盘超宽时把状态条折叠成两条固定在画布左右沿的小面板**。
3. 或：超宽时状态条只显示"雷数"一个元素并钉在画布右下角。

## 4.3 纵向溢出：抬档规则 + 状态条钉画布底边（v4.0 新增）

### 4.3.1 一句话新规则

> **「整块装得下」优先；但如果整块装得下的那一档格边 < 48 设备像素，就用更大的档位（允许纵向溢出）。**
> 纵向溢出时：**棋盘顶对齐菜单栏下沿**，**状态条钉在画布底边（像 HUD 一样）**，纵向平移上限 = **整个溢出量**。

这条规则的来源是用户原话：「**小到点不准比溢出更糟**」「**外屏不接受降级，我希望可以拖动放大**」。
它取代了 v3.0 的旧规则（旧规则还额外要求「抬完纵向装得下」才抬），**但保住了 L1 的结论**：
纵向装得下的时候不要乱抬（只有格边真的不足 48 px 才抬）。

### 4.3.2 Pura X Max 典藏版内屏 2584×1824 @2.75 · 自定义 24×30（新规则的唯一样板）

| 量 | v3.0（旧规则） | v4.0（新规则） |
|---|---|---|
| 适配档 n | 1 | **2** |
| 格边 | 36 px = 13.09 vp（点不准） | **72 px = 26.18 vp** |
| 棋盘尺寸 | 1080 × 1512 px | **2160 × 1728 px** |
| 棋盘原点 | (752, 477) | **(212, 58)**（顶对齐菜单栏下沿 58 px） |
| 棋盘 + 状态条包围盒 | (752,477 1080x928) | **(212, 58 2160×1856)** |
| 纵向溢出 | 0 | **90 px**（1856 + 58 = 1914 > 1824） |
| 棋盘可视区高 | 1766 | **1638**（菜单栏下沿 58 ~ HUD 顶 1696） |
| 纵向平移范围 | 无（不溢出） | **panY ∈ [-90, 0]**（单向，只能往上推） |
| 状态条带 | (752,1341 1080×64) | **(212, 1696 2160×128)** ← **钉在画布底边**，下沿正好 1824 = 画布高 |

**其余 15 组逐行逐字不变**（16 组总表只有这一行变了，脚本与本文都做了自动比对，见 §5.4）。

### 4.3.3 实现要点（`GameController.ets`）

1. **抬档**（`layout()`）
   ```ts
   if (TILE * 2 * fit < MIN_CELL_PX && fit < MAX_SCALE_INDEX) {
     const minTouchN: number = Math.ceil(MIN_CELL_PX / (TILE * 2));   // 48/36 -> 2
     fit = Math.min(MAX_SCALE_INDEX, Math.max(fit + 1, minTouchN));
   }
   ```
   与旧规则的区别：**不再检查「抬完纵向装不装得下」**，宁可溢出。

2. **摆位**（`applyGeometry()`）
   ```ts
   const groupFits: boolean = menuPx + boardH + stripH <= this.canvasH;
   const hudTop: number = this.canvasH - stripH;
   this.boardAreaH = groupFits ? availH : Math.max(1, hudTop - menuPx);
   const frameYBase: number = groupFits
     ? menuPx + Math.round((availH - boardH - stripH) / 2)   // 整组居中（16 组里 15 组走这条）
     : menuPx;                                               // 装不下 → 顶对齐菜单栏下沿
   this.stripTop = groupFits ? (this.boardY + boardH) : hudTop;
   this.hudActive = !groupFits;
   ```
   状态条的四个元素在 `drawStatusStrip()` 里一律锚 `this.stripTop`（不再用 `boardBottom`），
   所以 HUD 模式下计时与雷数永远看得见。横向那半边（两端贴画布沿）由主线程先修好，本次没动。

3. **纵向平移**（`clampPan()`）
   ```ts
   const boardH: number = e.rowCount * this.tile;
   const overV: number = boardH > this.boardAreaH ? boardH - this.boardAreaH : 0;
   this.panY = overV > 0 ? Math.max(-overV, Math.min(0, this.panY)) : 0;
   ```
   单向：默认 `panY = 0`（顶对齐），最多往上推**整个溢出量**；推到头时棋盘下沿与 HUD 上沿齐平，最后一行**完整可见**。

### 4.3.4 Codex 对抗性复审的两条（主线程跑的复审，裁定 BLOCKER）

| 编号 | 复审原文的判断 | 本次的处理 |

### 4.3.6 HUD 分支实测（2026-11-01，设备 5557 = Mate 90 Pro 模拟器）

### 4.3.7 状态条在「缩放」下的两组计数器（Codex 复审 P2，2026-11-01）

**问题**：状态条原来跟着棋盘的缩放档位一起放大（unit u = 2×n）。一组计数器
（时钟 25 + 间隙 6 + 面板 40 = 71 个参考单位）乘 u，两组就是 142u；
画布只有 1280 px 时 u 一旦超过 8 就放不下两组了，而贴边留白 `margin = 45u` 也在跟着涨。
Codex 实测：n=8、30 列、1280 宽屏时 margin=720px，**计时面板从 x=1216 起（大半在屏外），
雷数面板整个跑到屏幕外 —— 两个计数都看不见**。

**处理**（`GameController.drawStatusStrip`）：

| 改动 | 规则 |
|---|---|
| 内容自己一档 `su` | `su = min(u, 两组放得下的最大档)`，其中最大档 = `2×floor(canvasW/284)`；**必须是偶数**（图集是 2 倍存储像素，偶数档才是整数倍放大） |
| 贴边留白夹住 | `anchorMargin = min(margin, floor((canvasW − 2×71×su)/2))` |
| 两组不许互相压 | 右组整体要在左组右边：`iconX ≥ clockX + 71×su + 46×su` |
| 内容块位置 | `su === u` 时**与旧实现逐像素一致**（旧写法 `round((32−25)/2)×u = 4u` 不能改成 `round(3.5u)`，会差半格）；`su < u` 时在带子里居中 |

**结果**（`tools/check_layout.py` 断言 9，4 画布 × 4 盘面 × 极限档 n=8 全部通过）：

| 画布 | 极限缩放时的 `su` | 时钟 | 计时面板 | 雷数面板 | 雷图标 |
