## 0. 一句话结论

### 1.2 脚本口径

- `Math.round` 用 `floor(x+0.5)` 复刻（Python 内置 `round` 是银行家舍入，语义不同，必须自己写）。
- 平移量按"新局/未手动缩放"取 `panX = panY = 0`，即 `clampPan()` 不改变任何东西（`GameController.ets:235-239`）。
- 越界：矩形相对画布四边的余量出现负数。重叠：矩形相交面积 > 0。
- 整数像素：棋盘/底板/状态条四个元素的矩形、每一格的左上角、数字原点（`x+3u, y+1.5u`）、阴影条原点（`y+3u`）、状态条文字原点。

## 3. 核心问题：9×9 在宽屏上为什么只用掉约 59% 的宽度？

### 3.1 结论（一句话）

**`fitScaleIndex()` 约束的是"底板 frame"而不是棋盘**，而 frame 比棋盘多出 **59×62 个逻辑单位**的留白——这留白来自原版 Windows 窗口的玻璃边框，手机版**根本没画**（`drawBoardArea()` 只在棋盘矩形内填白地板加三边 1px 凹槽线，`GameController.ets:394-415`），于是这 59/62 单位纯属白占预算，把缩放档硬生生压低一到两档。

**最能说明问题的一行是 Mate X7 初级**：再上一档 n=5 时，frame 需要的宽度是 **2210 px —— 与画布宽度一模一样，差 0 px**，只差 32 px 的高度；而把这 59×62 留白拿掉，同一档只要 1620×1620，两边各富余 590/588 px。留白本身在 n=5 时相当于 590×620 px，比整个棋盘的三分之一还多。

**"约 59%"的出处**：Mate X7 内屏 2210 px 宽，初级棋盘 1296 px 宽 = **58.6%**（`GameController` 的 `layout()` 在这块画布上选了 n=4）。同一块画布上高级局却只用到 **48.9%**（1080/2210），因为宽度卡在 30 列上。

### 3.3 n 能不能更大？MAX_SCALE_INDEX=8 是死上限

- 上限本身：`Theme.ets:13` 的 `MAX_SCALE_INDEX = 8` → `u = 16` → 格边 288 px。
- **最小合法棋盘是 9 列**（`CUSTOM_MIN_COLS = 9`，`Theme`/`CustomField.ets:75`），9 列在 n=8 时棋盘宽 `9 × 18 × 16 = 2592 px`，**比最宽的画布（Pura X Max 内屏 2584 px）还宽 8 px**。
- 结论：**n=8 对任何合法棋盘、任何一块画布都到不了**（9 列最多 n=7，且 n=7 要 2268 px，只有 Pura X Max 内屏装得下）。卡住缩放的根本不是这个上限，而是 fit 公式。

## 4. 问题清单（按严重度）

### P0-1 · 高级/中级在 3 块画布上缩到 n=1，格边只有 10–13 vp，手指点不准

- **数字**：n=1 → 格边 36 设备像素。折算 vp：Pura X Max 外屏 13.09 vp、Mate X7 11.52 vp、Mate 90 Pro 10.29 vp。触屏可点尺寸一般在 40–48 vp 量级，**差 3–4 倍**。
- **涉及**：Pura X Max 外屏（中级/高级）、Mate X7（高级）、Mate 90 Pro（中级/高级）共 5 个组合。
- **源码**：`GameController.ets:237-247`（fit 循环）+ `Theme.ets:96-100`（FRAME_GAP_*）。
- **建议**：按 §3.4 的建议口径重算 fit（横向只算棋盘、纵向算 棋盘+状态条带+菜单栏）；再不够就允许棋盘超画布 + 拖动。改完 5 个组合里有 4 个能翻一倍。

### P1-2 · fit 把"画出来但看不见"的 59×62 单位留白算进了预算

- **数字**：横向白占 59 单位、纵向白占 62 单位。Pura X Max 内屏初级在 n=4 时**纵向差 148 px**（横向还富余 816 px），而 frame 的上留白 30 单位在 n=4 时正好是 **240 px** —— **把上留白砍掉就够**；横向同理，Pura X Max 外屏初级在 n=3 时**只差 3 px 宽**（1326 vs 1323）。
- **涉及**：`GameController.ets:240-241`（算 fw/fh）与 `GameController.ets:394-415`（`drawBoardArea` 只画棋盘矩形内的地板，三边 1px 凹槽线）。留白区在屏幕上就是背景色 `#c6cede`，没有任何视觉内容。
- **注意**：下留白 32 单位**不能全砍**——状态条带正好住在里面（见 P2-4）；上留白 30 单位则是纯浪费（手机版不画原版的上边框渐变）。
- **建议**：横向约束改 `cols*TILE*u <= canvasW`；纵向改 `rows*TILE*u + 32u + 菜单栏高 <= canvasH`。

### P1-3 · 菜单栏没有进竖向预算（现在不重叠，但放宽 fit 后必然重叠）

- **数字**：菜单栏固定 21 vp = 57.75 / 65.62 / 73.50 设备像素，画在画布顶部（`GameController.ets:1352-1357`）；棋盘却按 frame 在**整块画布**上居中（`GameController.ets:273-274`）。
- **现状**：12 个组合的棋盘上沿最少 234 px（Mate X7 中级），所以不重叠——**属于"恰好没碰上"**。按 P1-2 放宽后棋盘会长高，Mate X7 初级建议档 n=5 的棋盘高 1620 px + 状态条 320 px + 菜单栏 65.6 px = 2005.6 px ≤ 2208 px 仍装得下，但已经不宽裕；若再叠加上留白的居中偏移，棋盘上沿就会钻进菜单栏。
- **建议**：竖向预算显式包含菜单栏，并把 `applyGeometry()` 改成"从菜单栏下沿往下排"（而不是整块画布居中），上留白 30 单位直接取消。

### P2-4 · 状态条带 32u 借用的是原版窗口下边框的位置，取消左右留白后要重新确认

- **数字**：状态条带宽 = `32u`，与 frame 的下留白 `FRAME_GAP_B = 32` **完全相等**，所以状态条正好落在 frame 内、紧贴棋盘下沿、零重叠（`GameController.ets:668`）。
- **风险**：P1-2 若把横向留白取消（frame 宽 = 棋盘宽），状态条带的 x 起点仍是 `boardX`，宽度仍是棋盘宽，这条带子就变成"贴在棋盘下方、但由背景色托着"的一段，画布底部必须仍留得出 32u。
- **建议**：改 fit 时把 `32u` 明确写进竖向预算（已在 §3.4 的建议口径里），并确认 `drawStatusStrip()` 的 `boardBottom` 基准不变。

### P2-5 · 状态条两组元素锚在棋盘左右沿，真 Win7 锚在窗口左右沿

- **数字**：`GameController.ets:673`（时钟 = `boardX + margin`）、`GameController.ets:679`（雷图标 = `boardRight - margin - 25u`）。Mate X7 初级：状态条 1296 px 宽，画布 2210 px，左端空 461 px、右端空 453 px（棋盘没有精确居中，因为 frame 的左右留白 30/29 不对称）。
- **原版**：真 Win7 的雷数计数器是贴着**窗口**右边缘的（`helpBoard.png` 实测）。
- **定性**：**故意的**（手机没有窗口框，锚棋盘才对称）——但如果想更像原版，可把 margin 改成按画布宽度算，而不是按棋盘。

### P2-6 · 对话框/统计窗口的缩放是小数，按钮与文字落在非整数设备像素上

- **数字**：结束对话框 `s = max(1, min(2, canvasW/1400))` → Pura X Max 内屏 **1.8457**、Mate X7 **1.5786**；统计窗口 `s = canvasW/1500` → **1.7227 / 1.4733**。参考像素乘小数后，标题栏、按钮（`WinDialog.ets:204-206` 的 x=17/170/323、w=144）、文字全部落在半像素上 → 发虚，与"像素级复刻"的要求冲突。
- **涉及**：`GameController.ets:1039`（`dialogLayout`）、`GameController.ets:1110`（`statsLayout`）。
- **建议**：把 s 量化成整数档（1 或 2，或 0.5 步进），并在量化后用 `Math.round` 对齐原点。

### P2-7 · 自定义框 + 数字键盘用的是**陈旧的** dialogScale

- **链路**：`dialogScale` 只在 `dialogLayout()`（`GameController.ets:1039-1043`）里赋值，而它只被 `drawDialog()` 调用；`draw()` 的调用顺序是 `drawCustom()` **在** `drawDialog()` 之前（`GameController.ets:346-365`）；打开自定义框时 `this.dialog = null`（`GameController.ets:1203`）→ `drawDialog()` 直接 return → `customLayout()`（`GameController.ets:1209-1217`）拿到的永远是上一次的 `dialogScale`，首次为初始值 **1**。
- **后果**：自定义框的缩放恒为 **1**（陈旧初值），所以在任何画布上都是 402 px 宽（DLG_W 280 + 间隔 12 + 键盘 110）；Pura X Max 内屏的结束对话框却是 891 px 宽（**差 2.2 倍**），Mate X7 是 762 px（差 1.9 倍）。
- **建议**：把"算 dialogScale"抽成独立方法，`drawCustom()` / `customLayout()` 自己调用一次。

### P3-8 · 菜单栏下沿落在非整数设备像素，分隔线会发虚

- **数字**：`MENU_BAR_H = 21 vp` → 57.75 / 65.625 / 73.5 设备像素。分隔线 `WinMenu.ets:266` 用 `fillRect(0, 21, w, 1.1667)` 画在 vp 坐标上，上沿压在分数像素上。
- **建议**：菜单栏高度改成按设备像素取整，或把分隔线画成整 1 个设备像素。

### P3-9 · `MAX_SCALE_INDEX = 8` 对任何合法棋盘都是死上限

- **数字**：9 列在 n=8 时棋盘宽 2592 px > 最宽画布 2584 px（差 8 px）。9 列最多 n=7（2268 px），且只有 Pura X Max 内屏装得下。
- **建议**：上限本身无害，但要么降到 7（诚实），要么保留并在注释里写明"实际可达上限由画布决定"；真正的修法在 P1-2。

| 5 | 缩放是整数档 n=1..8，原版是固定 1:1 | 触屏需要放大；n 为整数保证素材 36 存储像素被整数倍放大（最近邻不糊） |
| 6 | 棋盘可平移、可捏合缩放 | 手机没有滚动条 |

### 5.2 意外的差异（= 问题清单，逐条对应）

| # | 差异 | 对应问题 | 性质 |
|---|---|---|---|
| 1 | fit 把不可见的 59×62 留白算进预算，缩放档小 1–2 档 | P1-2 / P0-1 | **遗留**：留白是原版窗口的遗留物，手机版不画却还在算 |
| 2 | 菜单栏不在竖向预算里 | P1-3 | **遗漏**：菜单栏是后来加的（SPEC §11.7），fit 公式没跟着改 |
| 3 | 对话框小数缩放 | P2-6 | **疏漏**：`canvasW/1400` 是随手写的比例，没做像素对齐 |
| 4 | 自定义框用陈旧 dialogScale | P2-7 | **顺序 bug**：`drawCustom` 与 `drawDialog` 的调用顺序与 scale 的赋值耦合 |
| 5 | 菜单栏下沿非整数像素 | P3-8 | **疏漏**：vp 常量没对齐到设备像素 |
| 6 | MAX_SCALE_INDEX=8 不可达 | P3-9 | **无害但误导**：上限是按"素材 2 倍 × 16"定的，没核过画布宽度 |
| 7 | 状态条带借用 frame 下留白 | P2-4 | **隐含耦合**：改 fit 时若把 32u 从预算里删掉，状态条会掉出画布 |
